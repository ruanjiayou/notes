# 分页接口技术规范

> **已废弃**：本文件由《分页缓存方案-v2.md》取代，勿再据此修改代码（v2 落地前已不再同步）。
> 本文与 `src/list-pagination.js` 保持同步（2026-09-23 全量对齐）。
> 命名、默认值、命令、上限一律以代码为准；README 是使用手册，本文是设计依据。

## 1. 范围与目标

本规范定义列表分页接口的排序模型、游标格式、读路径算法、缓存与 meta 结构，以及客户端与服务端的交互契约。

设计目标：

- 基于稳定全序的游标分页，避免 offset 分页的重复 / 漏读；
- 读路径单次 Redis 查询，无额外回源；
- 缓存失效、游标过期等异常情形均有确定行为，不静默截断；
- 不引入集中式序号服务。

## 2. 术语

| 术语         | 定义                                                              |
| ------------ | ----------------------------------------------------------------- |
| 锚点 anchor  | 本页最后一条已交付记录；游标的 `t` 取自它的 score                  |
| 探察项 probe | 第 `n+1` 条记录，本页不交付，只用于判断有无下一页并生成游标        |
| 全序         | `(score, id)` 上的确定顺序；ZSET 同分成员按 member 字节序排列      |
| member       | ZSET 成员，恒为 `id + '_' + type`（见 3.4）                        |
| 类型组合 combo | `types` 归一化后的组合名（`all` 或类型名排序后 `_` 连接）         |
| 水位线       | ZSET 尾部（展示序最后一条），扩展从它继续                          |
| 同分 band    | 一组 score 相同的成员                                              |

### 不变量

| 编号  | 内容                                                                                    |
| ----- | --------------------------------------------------------------------------------------- |
| INV-1 | `next` 为空 ⟺ 本次取数返回的记录数不足 `n+1` 条，且缓存已完整覆盖（`over == true`）   |
| INV-2 | 列表内的排列与源库 `ORDER BY scoreField DESC, id DESC` 完全一致（同分由 id 字典序定序），写入不伪造 score |
| INV-3 | meta 的 `count` / `over` 与列表数据同批次原子更新（一次 Lua）                          |
| INV-4 | 同一列表内 member 严格唯一（member = `id_type`，同一 id 不会以同类型重复入库）          |
| INV-5 | 游标失效时间不得超过列表缓存的存活时间                                                  |

## 3. 数据模型

### 3.1 排序键

排序键为 `fields[0]`（缺省 `modified_time`），毫秒精度。

- 新数据恒出现在列表头部，游标方向（由新到旧）与写入方向一致；
- **要求该字段写入后不再变化**：若可被改写，「翻页中排序值被改动」会让记录在列表中跳位，
  出现重复或漏读 —— 这是本设计排除失效模式的前提，由写入侧保证；
- 第二排序键固定为 `fields[1]`（缺省 `res_id`），用于同分收敛。

### 3.2 score 编码

- score 字段是**时间**（MySQL `DATETIME`，Sequelize 取出来是 `Date`），ZSET 的 score 是它的**毫秒数**：
  源库 -> ZSET 用 `new Date(record[fieldScore]).getTime()`，回查源库时的续点取自 ZSET 尾部、
  再 `new Date(tail.score)` 转回 `Date`（因为 MySQL 的时间列拿毫秒数去比是错的）——
  两个方向的转换**只在 `_extend()` 里各出现一次**，别处不再转换、也不做字符串往返；
- 除这一次「时间 -> 毫秒」的归一化，score 不做任何编码；
- **不存在「score 字段与排序字段不一致」这类配置错误**：`fields` 按位置解构
  `[fieldScore, fieldId, fieldType]`，`order` 由 `fields` + `rev` 现场推出：
  `order = [[fieldScore, 'DESC'|'ASC'], [fieldId, 'DESC'|'ASC']]`，两者天然一致，无需校验；
- 不使用微秒级基准，不使用位移编码，不在循环内 `+1ms` 伪造时间，不写 `head + 1` 兜底；
- 不提供 `scoreOf` / `valueOfScore` 之类的映射钩子：score 就是源字段的时间值本身（归一化成毫秒），
  多一层映射只会在扩展续点处引入错位；
- 所有写入路径（扩展、增量新增）走同一个取值口径：**ZSET 里的 score 恒为毫秒数** ——
  扩展路径由 `_extend()` 从源记录转出来，增量路径（`publish`）由调用方按同一个口径传毫秒数进来源。

新数据恒出现在列表头部；补录的旧数据按自己的时间戳落到列表的对应位置，不做任何改写。

### 3.3 精度边界

Redis ZSET 的 score 为 double，整数精确上限 `2^53 ≈ 9.007 × 10^15`。

| 写法            | 数值          | 结果                 |
| --------------- | ------------- | -------------------- |
| `modified_time` | ≈ 1.76 × 10¹² | 合法，余量到 2255 年 |
| `ms * 1e6`      | ≈ 1.76 × 10¹⁸ | 超精度，seq 被吞     |
| `ms << 20`      | ≈ 1.84 × 10¹⁸ | 超精度，seq 被吞     |

`score` 即毫秒时间戳，`ZCOUNT`、`ZREMRANGEBYSCORE` 等按时间范围的操作可直接使用。

禁止：微秒级基准；位移编码；在循环内 `+1ms` 伪造时间；写入时对 score 做任何改写（含 `head + 1`）。

### 3.4 存储结构

列表以 ZSET 存储，**member = `id` + `_` + `type`**，score 为 3.2 的值。缓存层只存 member 与 score，对象按 id 单独缓存。

member 恒带类型后缀、与类型组合无关：同一前缀下所有组合共用同一套 member 字符串，
写入侧（7.5）才能凭 member 反查类型、把变更投递给正确的组合。

```
member  =  id + '_' + type                 // 如 r003_article
```

**id 的两条硬约束**：

1. **等长**（uuid 36 位 / 定长 id）：等长时 member 前 36 字符就是 id，ZSET 同分按 member 字节序排、
   源库按 id 字段序排，两者才一致（否则 `r1_x` 与 `r12_y` 会反转）；顺带还要求排序用的
   id 列 collation 为二进制（如 MySQL `utf8mb4_bin`），否则源库的字符串序与 Redis 字节序不同；
2. **不含下划线**：全链路统一用 `member.split('_')` 反解 `[id, type]`，id 里带 `_` 会被截断。

key 三件套（前缀由构造参数 `key` 给出，如 `user:v6:history:user:xxx`）：

| key        | 组成                       | 说明                                             |
| ---------- | -------------------------- | ------------------------------------------------ |
| `keyList`  | `前缀 + ':' + combo + ':list'` | 列表 ZSET                                    |
| `keyMeta`  | `前缀 + ':' + combo + ':meta'` | meta 字符串（JSON）                          |
| `keyIndex` | `前缀 + ':idx'`            | 反向索引 SET，成员是 combo 名，同一前缀下所有组合共用 |

`types` 非 `'all'` 时，把它并入查询条件 `where[fieldType] = types`（Sequelize / Mongoose 的数组语义即 `IN`），
并据此收窄 combo 名。

## 4. 接口定义

### 4.1 请求参数

| 参数     | 类型   | 说明                                                       |
| -------- | ------ | ---------------------------------------------------------- |
| `cursor` | string | 游标，存在即走游标模式（需先 `decodeCursor` 解析再进类）    |
| `page`   | int    | 旧客户端兼容，仅在无 `cursor` 时生效，1 起                  |
| `size`   | int    | 本次窗口大小，缺省 15（`defaults.PAGE_SIZE`）               |

优先级（唯一口径）：

1. 有 `cursor` → 游标模式，忽略 `page`；
2. 无 `cursor`、有 `page` → 页模式，按 6.4 换算成 offset；
3. 两者皆无 → 首页。

`size` 是本次请求的窗口（上限），不是位置；翻页过程中允许改变页大小，服务端必须尊重新值。

**参数合法性一律由中间件把关**，类内只做三件事，且只有后两件会抛错：

- 不校验 `size` 上下限（中间件定，如「上限 100」）；
- 不校验 `page >= 1` 的整数性（中间件已保证；漏了会算出负 offset，Redis 直接报 `ERR offset is out of range`）；
- `cursor` 若传的是未解析的字符串 → 1402；页模式深度超限 → 1401。

### 4.2 响应结构

```typescript
type ListData<T> = {
  list: T[];                       // 恒为数组，不为 null
  next: string | null;             // null 即没有下一页，唯一结束信号
  total?: number;                  // 预留，本版本不返回（见 4.3）
};
```

列表项不带详情，至少含定位三元组，由调用方按 id 自取对象：

```typescript
type Item = {
  id: string;                      // 记录 id
  type: string;                    // 资源类型
  member: string;                  // ZSET member（= id + '_' + type）
  score: number;                   // = record[fieldScore]
};
```

### 4.3 total

**本版本不实现。** meta 里没有权威全量数，禁止在 SQL 上现场 `COUNT(*)`。

- Lua 里保留了 `if meta.total ~= nil` 的跟随分支：若将来由外部写入 `total`，增量路径会让它 ±1；
- 一旦启用，`total` 只是快照值，**禁止参与翻页边界计算**，与 `next` 是两套语义；
- 详见 7.2 的 `total` 行。

## 5. 游标规范

### 5.1 格式

```
cursor = base64url({ "t": 1770000000000, "m"?: "r003_article", "o"?: <int>, "e": 1770000014400 })
```

单段，无签名、无加密。必须使用 base64url（标准 base64 的 `+/=` 会在 URL 链路中被改写）。

当前载荷**没有版本字段**（原 `v` 已去掉）：解析只认 `t` / `m` / `o` / `e` 四个键，
多出来的键忽略、缺失的键按 5.4 处理（见 5.7 的演进规则）。

### 5.2 字段

| 字段 | 类型   | 必填 | 说明                                                                                     |
| ---- | ------ | ---- | ---------------------------------------------------------------------------------------- |
| `t`  | number | 是   | **探察项**（下一条待交付记录 `records[n]`）的 score，与读路径的**闭区间**配对使用（见 5.3）；毫秒时间戳数字，不做字符串往返 |
| `m`  | string | 否   | **探察项的 member**（`id_type` 整串）；仅当 `probe.score == anchor.score`（页边界落在同分 band 内）时携带 |
| `o`  | int    | 否   | 同分 band 内已交付成员累计数（含 anchor）；仅当页边界落在 band 内时携带，下页继续累加     |
| `e`  | int    | 是   | 失效时间，毫秒时间戳，服务端签发                                                         |

`m` 存的是 **member 整串**而不是 id：member 是 ZSET 内的真实比较对象，直接拿来比字节序即可，
不必再由 id 拼回 member，也避开了「同一 id 不同类型」的歧义。

游标是纯位置量：不含方向、不含归属、不含场景与排序规则。

### 5.3 生成

读取本页的 `n+1` 条记录（位置 0..n）：`records[0..n-1]` 是本页交付内容，`records[n]` 是**探察项**（probe，只用于判断是否存在下一页）。`next` 游标由本页尾部生成：

- `t = score[n]` —— **探察项**（下一条待交付的那条）的 score，语义是「下一页从这一条开始（含）」；
- `e = 本次响应时刻 + 有效期`。

`m` / `o` 携带规则：若 `score[n] == score[n-1]`（即 **probe.score == anchor.score**），页边界落在同分 band 内，游标同时携带：

- `m = member[n]`（探察项 member，即 band 内下一个待交付成员）；
- `o = (cursor.o or 0) + k`（仅当上一页的 `t` 与本页的 `t` 相同 —— 即两页边界落在**同一个 band** 内 —— 才累加，
  否则从 `k` 起算），其中 `k` 为本页已交付成员中 score 等于 `t` 的条数。

否则省略 `m` 与 `o`。

`m` 省略的安全性：`score[n] != score[n-1]` 说明本页恰好在 band 边界结束。下一页用**闭区间从 `t` 读起**，而 `t` 就是探察项（下一个 band 的第一条）的 score，所以正好从它开始，既不重复也不跳过。

> **删除兜底与定位**：下一页用闭区间 `t` 重新打开 band，再以 `m` 做**字节序**过滤（DESC 保留 `member <= cursor.m`，ASC 保留 `member >= cursor.m`，字符串直接比较，不用 `localeCompare`）。即使该成员已被删除（不在回复中）也能凭游标内的 `m` 继续正确定位，不空页、不漏读。
> `o` 只用于**收敛读取窗口**（见 6.2），不参与跳过：若 band 内已交付前缀中有成员被删，纯计数跳过会整体偏移而漏读，按 `m` 字节序比较则始终正确 —— `o` 管窗口、`m` 管正确性。
> 为什么 `t` 取 `score[n]`（探察项）而不是 `score[n-1]`（anchor）：**`t` 的取值与区间开闭必须配对**。取探察项配闭区间，语义就是「下一页从 `t`（含）开始读」，两种情形（边界是否落在 band 内）共用同一条取数规则，只是带 `m` 时窗口要放大、并过滤掉 band 内已交付前缀。已交付成员的 score 都 `> t`（否则它们会与探察项同分），闭区间不会把已交付的带回来。反过来的组合（`score[n-1]` + 开区间）选中同一批记录、同样正确，只是要多一个「同分开、非同分开」的分支。**踩过的坑是配错**：`score[n]` 配开区间会丢掉探察项所在的**整个同分块**（不止一条），`score[n-1]` 配闭区间则重复交付该 band 里已交付的成员 —— 改动 `t` 时务必对照 6.2 的三个分支。

### 5.4 校验

```
1. base64url 解码 → JSON 解析                 失败 → 1402
2. 载荷是对象（非数组 / 非 null）              失败 → 1402
3. t 是有限数字                               失败 → 1402
4. e 存在且可解析、且 e > 当前时刻              否则 → 1403
```

返回值归一化为 `{ t, m, o }`：`m` 不是非空字符串则为 `null`，`o` 不是正整数则为 `0`
（即「游标里没有定位信息」与「有定位信息」两种形态）。校验函数是 `decodeCursor(raw, now)`，
**在类外、但同一个文件里**，类只接受解析后的对象 —— 直接塞字符串进 `paginate` 会抛 1402。

校验失败返回对应错误码（1~3 → 1402，4 → 1403），禁止降级为「当作首页」。

### 5.5 安全约束

游标可被客户端构造，因此：

1. 列表 key、排序规则、页大小上限必须由服务端从 session 与 query 推导，不得从游标内容取信
   （类里除 `cursor` 外的参数全部来自实例自己的 `this.opts`，不从游标取信）；
2. 游标不得参与授权判定，每次请求照常鉴权；
3. 深度限制与限流照常生效，合法游标不免除限流；
4. `e` 同样可被客户端延长，禁止用 `e` 承担限流、配额或授权职责。

### 5.6 有效期与续期

| 项   | 规则                                       |
| ---- | ------------------------------------------ |
| 取值 | 4 小时（`defaults.TTL_SEC`，与列表 / meta / 索引同一个 TTL） |
| 续期 | 滑动：每次返回 `next` 时以当前时刻重算 `e` |
| 上限 | 有效期 ≤ 列表缓存存活时间（INV-5）         |
| 超期 | 返回 1403，客户端重置到首页                |

滑动续期约束的是闲置时长，不是会话总时长。

### 5.7 版本演进

载荷当前无 `v`。以下变更必须视为**不兼容变更**，且必须在 `decodeCursor` 里显式拒绝旧载荷：

- 排序规则或场景语义变化；
- 载荷字段含义或编码变化（如 `m` 改为存 id 而不是 member）；
- 游标需要携带新的定位维度（如分桶后的 `bucket`）。

做法：新增必填字段时，旧游标因缺字段按 1402 拒绝；字段含义变化时**复用一个新键名**，
使旧键既不出现也不被误读。若将来需要同时兼容多个版本，再加回 `v` 并由 `decodeCursor` 分支处理。
`decodeCursor` 是唯一解析入口，演进只改这一处。

## 6. 读路径算法

### 6.1 主流程

```
输入：游标 cursor（首页为 null）、页大小 n

1. meta = GET keyMeta；不存在则 _extend() 建立缓存
2. items = _read(cursor, n)                        // 按 6.2 取 n+1 条
3. while items.length <= n && meta.over !== true:
       before = meta.count
       meta = _extend()                            // 固定再取 step 条
       if meta.count == before: break              // 水位线推不动，防空转
       items = _read(cursor, n)
4. if items.length <= n && meta.over !== true:
       throw 1500                                  // 拒绝静默截断

组装：
  list = items[0..n-1]                             // n 条交付
  next = items.length > n ? 生成游标(见 5.3) : null
```

第 3 步是「缓存不足 → 扩展」的唯一入口，第 4 步守住 INV-1：`over == true` 与「取数不足 `n+1` 条」必须同时成立才判结束。二者落到同一分支会使列表在某个深度被永久截断且无报错。

扩展次数有天然上界：每次 `_extend` 固定取 `step` 条且必须推进水位线（否则 `break`），
所以循环次数 ≤ 源库总量 / `step`。

### 6.2 取数与同分处理

读路径统一使用 `ZREVRANGEBYSCORE`（倒序）/ `ZRANGEBYSCORE`（正序）**按 score 查询**；
不使用 `ZREVRANK` / `ZRANK` / `ZREVRANGE` / `ZRANGE` 做游标读取。这是排序一致性的前提（见 6.3）。

> **实现口径（redis@4.6.7）**：这两个命令由 `sendCommand` 直发，参数全部为字符串 ——
> `sendCommand([rev ? 'ZREVRANGEBYSCORE' : 'ZRANGEBYSCORE', keyList, 高, 低, 'LIMIT', String(offset), String(count), 'WITHSCORES'])`。
> 不用封装方法的原因（实测其 `transformArguments`）：
> `zRangeByScore(k,a,b,{WITHSCORES,REV,LIMIT})` 只生成 `ZRANGEBYSCORE k a b LIMIT …`，
> `WITHSCORES` 与 `REV` 被**静默丢弃**（拿不到 score，且永远升序）；
> `zRangeByScoreWithScores` 补上 `WITHSCORES` 但仍丢 `REV`；`zRevRangeByScore` 该版本未提供；
> 唯一带 score + 倒序的封装是 `zRangeWithScores(k,a,b,{BY:'SCORE',REV,LIMIT})`，
> 但它要求 **Redis ≥ 6.2**，而 `ZREVRANGEBYSCORE` 自 Redis 1.0.5 起即有。
> 代价：回复是扁平数组 `[member, score, …]` 且 score 是字符串，实现里手工配对并 `Number()`。

取数恒为 `n+1` 条：前 `n` 条交付，第 `n+1` 条是探察项。

**首页**

```
DESC: ZREVRANGEBYSCORE key +inf -inf LIMIT 0 n+1
ASC : ZRANGEBYSCORE    key -inf +inf LIMIT 0 n+1
```

**游标无 `m`（页边界不在 band 内）**

```
DESC: ZREVRANGEBYSCORE key t -inf LIMIT 0 n+1      // 含 t，闭区间
ASC : ZRANGEBYSCORE    key t +inf LIMIT 0 n+1
```

`t` 就是探察项的 score，闭区间正好从探察项开始；本页已交付成员的 score 都 `> t`（否则它们会与探察项同分，就落到下面那一支了），所以一条都不会被重复带回来。

**游标有 `m` / `o`（页边界落在 band 内）**

```
span  = o + n + 1                                   // 收敛窗口；初值故意不设上限
loop:
  raw   = DESC: ZREVRANGEBYSCORE key t -inf LIMIT 0 span        // 含 t，闭区间
          ASC : ZRANGEBYSCORE    key t +inf LIMIT 0 span
  items = [x for x in raw if x.score != t or (DESC: x.member <= cursor.m | ASC: x.member >= cursor.m)]
  if len(items) > n or len(raw) < span or span >= MAX_SCORE_BAND: return items
  span  = min(span * 2, MAX_SCORE_BAND)             // o 被低估 -> 窗口吃满，放大重读
```

- 过滤只作用于 band 内（`x.score == t`）的成员；score 更深的成员本来就未交付，必须保留；
- 保留侧是「本页尾部之后」的成员：DESC 下 band 内 member 降序，探察项及其后续都满足 `member <= cursor.m`；
- 闭区间 `t` 会重复返回 band 内已交付过的成员，但不会漏；重复由客户端按 id 去重吸收；
- `o` 只用于把读取窗口从「整条 band」收敛到 `o + n + 1`，避免每次都扫描全 band；
  窗口被读满且过滤后仍不足 `n+1` 时按 2 倍放大重读（上限 `MAX_SCORE_BAND = 800`），
  因此 `o` 被低估时只会多读，不会漏；
- **初始 `span` 故意不加 `MAX_SCORE_BAND` 上限**：窗口 W = o + count、真实前缀 o_true 时
  `kept = W - o_true`，只有 W 跟着 o 走才能保证常态下 `kept = count`（第一轮就成功）；
  给初值设上限会让长 band 的 `kept` 随 o 增长而缩水，返回不足 `n+1` 条，
  此时若 `over` 已为 true 就会给 `next = null` —— **静默截断**。上限只管「放大」那一段；
- **band 内禁止用 offset 跳过前缀**：`o` 是「已交付成员数」这个计数，而 `LIMIT` 的 offset 是
  ZSET 里的**物理位次**；前缀（排在 `m` 正上方）被删除几条后 offset 会整体右移、越过 `m` 本身，
  漏读恰好发生在游标边界。所以窗口恒从 offset 0 起读，靠 member 比较过滤；
- `m` 指向的成员已被删除时它不在 `raw` 中，字节序比较仍落在正确位置，不空页、不漏读。

### 6.3 排序一致性

同分 band 内，ZSET 成员按 member 字节序排列，该顺序是 Redis 确定的、稳定的。

member = `id_type`，而 id 等长且不含下划线、type 只有几个字符，因此 member 的字节序
**在 id 段内等价于 id 的字节序**（type 后缀只在 id 完全相同时才参与比较，而同一 id 的类型唯一）。
这是「ZSET 顺序 == 源库 `ORDER BY scoreField, id`」的成立条件，也是 3.4 那两条 id 约束的由来。

排序一致性要求：**整个翻页过程只使用 BYSCORE 系列查询**（`ZREVRANGEBYSCORE` / `ZRANGEBYSCORE`）。

- 混用 `ZREVRANGE` / `ZREVRANK`（按 rank）与 `ZREVRANGEBYSCORE`（按 score）会导致同分 band 的遍历顺序在不同页之间不一致，表现为数据乱序或重复 / 漏读；
- 禁止用 `ZRANGEBYLEX` 做 band 内定位（成员 score 不同时行为未定义）；
- 禁止用返回数组长度判断结束（结束只由 `next` 是否存在决定）。

### 6.4 页模式兼容

```
offset  = (page - 1) * size
depth   = offset + size + 1                          // 缓存至少要覆盖到这里

meta = GET keyMeta
while !meta || (meta.over !== true && meta.count < depth):
    before = meta ? meta.count : -1
    meta = _extend()                                 // meta 不存在时即从源库建缓存
    if meta.count == before: break                   // 水位线推不动，防空转

records = DESC: ZREVRANGEBYSCORE key +inf -inf LIMIT offset (size + 1)
          ASC : ZRANGEBYSCORE    key -inf +inf LIMIT offset (size + 1)
list    = records[0 .. size-1]
next    = records[size] 存在 ? 按 5.3 生成游标 : null
```

换算后汇入 6.1 链路（同样取 `size + 1` 条，多出的一条作探察项）。
页模式与 `cursor()` 同构：**先读 meta，再在函数里判断**，没有独立的 `_ensureDepth()`，逻辑就写在 `page()` 里。约束：

- 取页同样只用 `ZREVRANGEBYSCORE` / `ZRANGEBYSCORE`，整个读路径只有一种查询形式（6.3 的排序一致性要求覆盖页模式）；
- **`page` 的合法性（≥ 1 的整数）不在类内校验**，由中间件保证；类内只查深度上限；
- 深度限制：`offset + size > MAX_PAGE_DEPTH`（默认 **10000**）抛 1401，要求客户端改用游标；
- 漂移问题在页模式下持续存在，属 offset 固有性质，写入契约作为已知行为。

## 7. 缓存与 meta

### 7.1 分层

| 层   | 内容                      | 说明                                 |
| ---- | ------------------------- | ------------------------------------ |
| 对象 | 按 id 单条缓存            | 单对象变化只失效一个 key（本设计外） |
| 列表 | 只存 member **+ score**   | 游标推进依赖 score，必须一起存       |
| meta | 见 7.2                    | 每个「前缀 + 组合」一份              |
| 索引 | combo 名集合（SET）       | 写入侧找候选列表用，见 7.5           |

禁止缓存整页结果：一页内任意一条变化即导致整页失效。

三层（列表 / meta / 索引）**同一个 TTL、同批次续期**，见 7.4。

### 7.2 meta 字段

| 字段    | 含义                                      | 存储形式 | 必填 |
| ------- | ----------------------------------------- | -------- | ---- |
| `over`  | 缓存是否已完整覆盖全量列表                | bool     | 是   |
| `count` | 缓存内记录数（== `ZCARD`，监控 / 对账用） | 整数     | 是   |
| `total` | 全量条数（展示用快照，非权威）            | 整数     | 否（本版本不写） |

就这两个字段：一次 `GET keyMeta` 拿到「有多少 + 到没到底」，比「读 meta 再补一次 `ZCARD`」更快，JSON 也短。

`over` 取代「比较列表端点」的结束判定：建立缓存 / 扩展时，当某次从数据库取页返回记录数少于请求量（短页），即说明已到全量末尾，置 `over = true`。无需任何查询全量端点的额外语句。`over` 对写入不敏感（插入 / 删除均不改变「已覆盖到末尾」的事实）。

**续点不落 meta**：扩展时直接探针 ZSET 尾部 —— 倒序 `ZRANGE key 0 0 WITHSCORES`、升序
`ZREVRANGE key 0 0 WITHSCORES`（下标 0 恰是展示序的最后一项），`id` 由 member `split('_')` 拆出。
读的就是 ZSET 本身，不存在「meta 里的副本与集合脱节」。两点附带好处：`publish(-1)` 删掉尾部成员后
续点自动跟着新尾部走；`list` 单独丢失而 `meta` 幸存时，`count` 与 `ZCARD` 的差异会触发重建。

`count` 由 Lua 内 `ZCARD` 直接重算（扩展路径）/ ±1 维护（增量路径），仅用于监控与「缓存是否覆盖到目标深度」的判断，**禁止参与结束判定**（结束只看 `over` + 取数是否足量）。

`total` 本版本不写；Lua 只在 meta 里**已有** `total` 时让它随增删 ±1，供将来外部维护。

### 7.3 更新规则

**扩展路径（权威）** —— `_extend()`：

- 每次**先读 meta**（`count` / `over`）判断，再从 **ZSET 尾部**续点取数；
- 每次固定取 `step` 条（默认 200），不随翻页深度变化；
- **`step` 必须 ≥ 2**：续点是闭区间（同分用 `Op.lte` / `Op.gte`），每批都会重取边界那一条
  （`ZADD` 幂等，重复无害），`step = 1` 时净推进为 0 → 水位线推不动 → 短页或 1500；
- 续点条件（`Op` 来自 `require('sequelize')`，倒序为例；`s.score` 是毫秒数，
  **必须 `new Date(s.score)` 转回 `Date`** —— 时间列直接比毫秒数 MySQL 会按字符串比较而错位）：

  ```js
  const at = new Date(s.score);
  where[Op.or] = [
    { [fieldScore]: { [Op.lt]: at } },
    { [fieldScore]: at, [fieldId]: { [Op.lte]: s.id } },   // 升序用 Op.gt / Op.gte
  ];
  ```

- `ZADD` 一批数据 + 重算 `count` + 维护 `over` + 续期三键 + 登记反向索引：
  **一次 `eval` 原子完成**（`LUA.EXTEND`）。
- 当本次取到的数据库记录数少于请求量（`members.length < step`）时，置 `over = true`；
- **允许并发扩展，不使用单飞锁**：`ZADD` 幂等、续点取自 ZSET 只会被推进到同一位置，
  重复扩展无副作用，因此不引入锁 / 等待轮询，也不返回 1429；
- 扩展是**唯一**的缓存建立入口（首次请求与页模式都走它），它同时负责把 combo 登记进反向索引。

**增量路径（旁路）** —— 静态 `publish(key, value, score, action, ttl)`，**仅在目标组合的 meta 存在时执行**

| 操作 | 行为                                                                                               |
| ---- | -------------------------------------------------------------------------------------------------- |
| 新增 | `ZADD` + `count + 1`；`over` 不变；meta 不存在则**不写缓存、不建索引**                              |
| 删除 | `ZREM` + `count - 1`；**归零也不摘索引**（见下）；meta 不存在则从索引剔除该组合 |

- 写入不伪造 score：直接用记录自带的 `fieldScore` 值，按 3.2 的口径归一化成毫秒数传给 `publish`
  （时间转毫秒这一步在业务侧调用处做，类里只按 3.2 处理扩展路径；不 `+1ms`、不 `head + 1`）；
- 增量路径允许失败：meta 不是唯一真相，允许丢失与暂态不一致，由下次扩展重算覆盖；
- 续点本就取自 ZSET 尾部，无需重建；
- **删空不摘索引**（踩过的坑）：`count` 归零时若顺手 `SREM` 掉组合，该组合就从索引里消失了 ——
  之后的新增在步骤 1 拿不到它，新记录进不了 `list`；而 `meta` 仍是 `{count:0, over:true}`，
  读路径判定「缓存已到底」不再扩展，于是**列表一直返回空，直到 TTL 过期才自愈**。
  空组合留在索引里的代价只是一次空转的 `eval`（`ZADD`/`ZREM` 返回 0）；
  删空时 `list` 这个 key 会被 Redis 自动删掉（空 ZSET 不保留），下次 `ZADD` 重新建起来即可。
  索引的收敛只剩两条：`_extend()` 的幂等 `SADD`，以及这里遇 -1（缓存没了）时的 `SREM`。

### 7.4 一致性要求

| 组     | 字段                     | 要求                                      |
| ------ | ------------------------ | ----------------------------------------- |
| 权威组 | `over`                   | 必须与列表数据同批次原子更新（INV-3）     |
| 可选组 | `count`                  | 允许暂态偏差，可被重算覆盖，仅监控        |
| 预留   | `total`                  | 本版本不写                                |

meta 与列表数据同生命周期，做法是**列表 / meta / 索引三键同一个 TTL、每次写入一起续期**
（不用 `cache_epoch`）。否则 `over` 会失真、
INV-1 判定失效，表现为静默截断。这也是 INV-5「缓存存活时间」的可定义前提。

### 7.5 反向索引（一个 id 属于多个子列表）

同一前缀下每个**已创建缓存**的组合名都登记在 `keyIndex = 前缀:idx` 这个 SET 里，并随之续期：

```
SADD   keyIndex combo           // 在 EXTEND Lua 内，幂等
EXPIRE keyIndex ttlSec
```

写入侧只拿得到「key 前缀 + member + score」，不知道该落到哪些组合，因此：

```
publish(key, member, score, action, ttl) -> { value, changed, stale }

1. combos = SMEMBERS 前缀:idx
2. 对每个 combo：
   a. 类型筛选：member 后缀即记录类型（见 3.4）；combo == 'all' 通吃，
      否则要求 combo 名（'_' 分隔的类型列表）含该类型，不含则跳过
      （既不算 changed、也不算 stale，TTL 都不动）
   b. eval(LUA.CHANGE, { keys: [list, meta, idx], arguments: [add|del, member, score, ttl] })
   c. 返回 -1  -> meta 不存在（缓存已过期）：SREM keyIndex combo，记入 stale
      返回 0   -> 受理但无变更（ZADD / ZREM 未命中）：只续期，两边都不记
      返回 1   -> 确实变更，记入 changed
```

- **反向索引只在组合真正有缓存时存在**，因此「新增」不会为不存在的缓存建索引；
- `action > 0` 为新增，否则为删除；同一 member 重复写是幂等的（由 `ZADD` / `ZREM` 的返回值决定计数）；
- 新增记录不会「插队」到已翻过的页：它的 score 决定位置，按 score 区间翻页天然一致；
- `publish` 是静态方法，只传 key 前缀，不需要实例（写入侧通常拿不到 `where` / `types`）。

## 8. 列表分片（可选）

分页开销为 `O(log N + n)`，与列表长度无直接关系。分片的动机是运维与热点，不是分页查询性能。

触发信号：单 key 成员数千万级；单 key 内存百 MB 以上（member 约 44 B + skiplist 开销，1000 万 ≈ 1 GB）；单 key 成为 QPS 热点；`ZREMRANGEBYSCORE` 一次删除几十万条阻塞主线程。

维度优先级：

1. 天然分片优先：`history:{uid}`、`comment:{songId}` 等按对象分片的 key 本身是小列表，无需额外拆分；
2. 时间分桶：`list:{scene}:2026-09`，与「时间倒序、由新到旧」同向，老桶到期用 `UNLINK` 整桶删除；代价是游标需跨桶，页跨桶边界需拼接二次截断；
3. 冷热分离：热段留 ZSET，旧数据落库；
4. hash 分片：不建议，分页需归并 N 路。

分桶变更游标格式，按 5.7 处理。

## 9. 监控

| 项               | 触发条件                                    | 采集点 |
| ---------------- | ------------------------------------------- | ------ |
| 同分 band 过长   | band 长度 > 256                             | 读侧   |
| 游标过期率       | 过期请求占比异常偏高                        | 读侧   |
| score 与头部倒挂 | 写入 score 低于列表头部 score（补录旧数据 / 时钟回拨） | 写侧   |
| 水位线停滞       | over==false 时扩展取不到新数据（`count` 不涨） | 扩展侧 |
| meta 缺失        | 有列表数据但无 meta                         | 巡检   |
| count 偏差       | `count` 与 `ZCARD` 长期不符                 | 巡检   |
| 索引残留         | `keyIndex` 里的 combo 存在但 meta 已过期     | 巡检   |

同分 band 长度仅作数据质量指标：band 过长说明批量写入时间戳粒度过粗，页边界频繁切在 band 中间，
每次都要回读 band 前缀（6.2 的固有开销）。

离线巡检：分批 `ZRANGE key start stop WITHSCORES`（按下标分批，仅对账用）比较相邻 score，
重点抽查批量写入密集时段。

## 10. 一致性语义

| 操作       | 翻页过程中的表现                                              |
| ---------- | ------------------------------------------------------------- |
| 新增       | 出现在头部；插在锚点之前时本次翻页不可见（属契约约定）        |
| 删除       | 翻页中消失；删掉锚点所在 band 的成员时走 6.2 闭区间逻辑，可能重复，不会漏 |
| 改排序值   | 本设计下不发生（3.1 要求排序键不可变）                        |
| 重复请求   | 幂等，返回同一页                                              |
| 改变页大小 | 服务端必须尊重新值                                            |
| 游标非法   | 返回 1402，禁止降级为首页                                     |
| 游标过期   | 返回 1403，客户端重置到首页，禁止复用同一游标                 |

读己之写在分页接口上不保证，需要时由「写入后返回新游标」或前端局部插入实现。

## 12. 客户端约定

- 按 id 去重，不得假设不重复（降级路径与同分边界都会产生重复）；
- 用 `next` 是否为 null 判断结束，禁止用数组长度；
- 游标为不透明字符串，禁止解析、禁止截断；
- 收到 1403 时丢弃当前分页状态，重新请求首页，禁止用同一游标重试；
- 页大小是本次窗口，可在翻页中调整；
- `total` 本版本不返回，拿到也只作展示、不得用于计算页边界。

## 13. 实施检查清单

**数据模型**

- [ ] 排序键为 `fields[0]`（缺省 `modified_time`），写入后不再变化
- [ ] score 直接使用 `fields[0]` 的值，未使用微秒或位移，写入不伪造（无 `+1ms` / `head + 1`）
- [ ] `fields` 按位置解构 `[scoreField, idField, typeField]`，`order` 由 `fields` + `rev` 现场推出
- [ ] member 恒为 `id_type`；id **等长**且**不含下划线**；id 列 collation 为二进制
- [ ] key 三件套：`前缀:组合:list` / `前缀:组合:meta` / `前缀:idx`
- [ ] `types` 非 `all` 时并入 `where[fieldType]`，并据此收窄 combo 名

**游标**

- [ ] 游标为 `base64url({t, m?, o?, e})`，`t` 为数字，无 `v`
- [ ] `t = score[n]`（**探察项** —— 下一条待交付记录）的 score，与闭区间配对使用
- [ ] `m` 为**探察项 member 整串**，`o` 为 band 内已交付累计数；两者仅在 `probe.score == anchor.score` 时携带
- [ ] 游标校验失败返回 1402，未降级为首页；`e` 超期返回 1403
- [ ] `e` 为滑动续期，且不超过列表缓存存活时间（INV-5）
- [ ] 解析入口唯一（`decodeCursor`），类只接受解析后的 `{t, m, o}`；传字符串抛 1402
- [ ] 列表 key、排序规则、页大小上限均由服务端推导，未从游标取信

**读路径**
