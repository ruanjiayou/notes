# 列表分页缓存设计

## 背景与原因

用户数据（如订阅、历史记录、收藏）在列表接口里需要按时间倒序分页展示。直接对数据库做 `OFFSET` 深翻页有两个问题：一是数据量大时越翻越慢，二是翻页期间数据增删会造成上下页重叠或漏数据。为此引入 Redis ZSET 作为排序缓存：列表只缓存「id + 类型 + 时间」，详情仍由调用方按 id 自行读取；排序与翻页全部落在 Redis 上，数据库只在缓存未覆盖到目标深度时被少量读取。

## 目标 / 要解决的问题

- 支持两种分页方式：`page`（按页码 `page/page_size`）与 `cursor`（按游标 `cursor/limit`），游标优先。
- 用 ZSET 把「按时间排序」缓存起来，翻页只打 Redis，深翻页不直接对库做 OFFSET。
- 处理时间字段**同分**（多条记录同一毫秒）时不能漏读、不能重复交付。
- 数据增删时通过旁路增量（`publish`）实时维护缓存，避免缓存与库长期漂移。
- 缓存 key 需要适配 Redis Cluster（proxy 集群），跨 key 的 Lua 脚本必须落在同一 slot。
- 规避已知坑：源库是 **MongoDB**，时间字段是 `Date`，但脏数据（字符串 `'0000-00-00 00:00:00'`、`null` 之外的各种非法值）转毫秒数仍会得到 `NaN`，`ZADD` 收到 `NaN` 会直接报 `ERR value is not a valid float`。
- 同一份列表要能同时服务**降序**（时间从新到旧）和**升序**（时间从旧到新）分页：排序方向 `rev` 是**实例级**参数（构造函数给定，缺省降序），**每个方向各持一份缓存**（原因见下）；要双向就按同一 `key` 建两个实例。

## 解决方案概览

用 Redis ZSET 作为排序缓存，`score` 存时间字段的毫秒数，`member` 统一为 `id_type`。每个「类型组合 × 方向」各持一份 list + meta：

```
keyList = {prefix}:{combo}:{dir}:list     ZSET    排序列表，score = 时间毫秒数，dir ∈ {desc, asc}
keyMeta = {prefix}:{combo}:{dir}:meta     STRING  元数据（一个整数：源库总条数 total）
keyIdx  = {prefix}:idx                    SET     反向索引，成员是 `${combo}:${dir}`（如 all:desc）
```

其中 `prefix` 就是构造时传入的 `key`，命名规范为：

```
user:v6:{ownerType}:{uuid}:history:{scene?}:{scoreField}
例：
user:v6:user:{uuid}:history:act_time                  自己（ownerType=user）的某列表，分数字段 act_time
user:v6:user:{uuid}:history:subscribe:act_time        「我关注了谁」，分数字段 act_time
user:v6:{ownerType}:{uuid}:history:fans:act_time      「谁关注了我」，ownerType ∈ {user, subscription}
```

- **`prefix` 最后一段（最后一个 `:` 后面）固定是分数字段名**，`scoreField` 直接从 key 里解出来，不再由 `fields` 传。上面例子里都是 `act_time`。
- `ownerType` 区分列表宿主实体类型：普通用户是 `user`，订阅号 / 订阅实体是 `subscription`。一段 uuid 即宿主 id。
- `combo` 是类型组合：`all` 表示全部类型，否则为 `types` 排序后按下划线连接（如 `article_ticker`）。
- `dir` 是排序方向：`desc`（降序，时间从新到旧）/ `asc`（升序，时间从旧到新）。
- `member` 恒为 `id + '_' + type`，与组合、方向都无关，同一前缀下所有缓存共用同一套 member 字符串。
- **硬约束**：`id` 必须**等长且不含下划线**。等长才能让 ZSET 同分按 member 字节序排 == 源库按 `_id` 排；不含下划线才能用 `member.indexOf('_')` 反解出 `[id, type]`。源库 MongoDB 的 `_id` **统一是字符串**（如 24 位 hex 串），keyset 直接按字符串比，不做 ObjectId 转换。
- `score` 字段是时间（MongoDB `Date`），进 ZSET 前转成毫秒数。
- 前缀 key 中的 uuid 用 hash tag `{uuid}` 包裹，使 `list` / `meta` / `idx` 所有键落同一 slot，适配 Redis Cluster 的多 key Lua。

### 为什么方向必须进 key

ZSET 里缓存的是**一段连续区间**，而「该从哪一端开始读」由请求方向决定：

- **降序**要从**最新端**（max score）往下读，所以缓存必须贴着最新端往早端生长；
- **升序**要从**最旧端**（min score）往上读，所以缓存必须贴着最旧端往新端生长。

一段区间不可能同时贴住两端（除非把整个列表全量缓存）。若两个方向共用一份 list，会出现两种错误：

1. **读到错误的起始位置**：降序建的缓存（比如只覆盖最新 200 条）被升序请求拿去读，升序首页会返回这段区间里最旧的若干条，而不是库里真正最旧的记录；
2. **区间被撕成两段产生空洞**：升序先建（覆盖最旧一段）、降序再读时又往最新端扩，中间那段缺失，翻页会从最新段直接跳到最旧段，还谎报「已到底」。

所以方向是 key 的一部分：两个方向各自维护自己的 list，各自从自己那一端起读、往自己那一端扩，互不干扰。

### 方向怎么落到实例与索引上

- **实例一个方向**：`rev` 在建实例时给定（缺省 `true` 降序），实例内所有读写都用它派生的 key。分页方法与游标都不再关心方向，业务要双向就按同一个 `key` 建两个实例，请求侧按 query 参数（如 `sort=desc`）挑实例。
- **索引只有一份**：`{prefix}:idx` 不带方向，成员是 `${combo}:${dir}`。`publish(key, ...)` 只收 prefix，靠这份索引把新数据**一次喂给已存在的两个方向**——写入侧无法预知之后会被哪个方向读到，只维护一边必然出现「降序看得见、升序看不见」；若索引也按方向拆开，业务就得为同一批数据调两次 `publish`。
- **没被读过的方向不建缓存**：某个 `dir` 从没被读过，索引里就没有它的成员，`publish` 自然跳过；索引里有成员但它的 `meta` 已过期（脚本返回 -1）时，只摘掉那一个成员，另一个方向不受影响。

### 关注场景要维护的两个 key

A 关注 B（B 可能是 `user` 也可能是 `subscription`）时，一次写入要同时落到两个缓存：

| 列表      | key（prefix）                                         | 写入的 member             |
| ------- | --------------------------------------------------- | ---------------------- |
| A 的订阅列表 | `user:v6:user:{A.uuid}:history:subscribe:act_time`  | `${订阅行的 id}_${B.type}` |
| B 的粉丝列表 | `user:v6:{B.type}:{B.uuid}:history:fans:act_time` | `${粉丝行的 id}_${A.type}` |

- 两个 key 分别落在**各自的 hash tag slot**，所以是两次独立的 `publish`，不能放在同一段 Lua 里。
- member 的 `id` 段 = `fields[1]`（默认就是 `_id`）：**用「各自集合里刚写入那行的 id」，不是 B 的 id**。因为 ZSET 的同分顺序必须与源库排序一致，而源库排序的兜底字段就是 `fields[1]`；业务 id（`res_id` / `from_id`）留在文档字段里，调用方按 member 的 id 回表取详情。源库 `_id` 是等长字符串，天然满足「等长 + 无下划线」。
- 类型过滤天然对齐：订阅列表里的 member 类型是「被关注方类型」（B），粉丝列表里的 member 类型是「关注方类型」（A），两边 `publish` 传的 member 本来就不同。
- **不额外封装**：两个 key 各调一次 `UserPaginatorCache.publish()`，由业务自己串（不同 slot 本来也放不进同一段 Lua）。

## 元数据 meta

meta 就是**一个整数字符串**，每个「组合 × 方向」各一份，只存源库总条数：

```
{prefix}:{combo}:{dir}:meta   →   "137"     // 源库符合该组合的总条数
```

- `total` 在**首次建缓存那一次**由 `model.countDocuments()` 得到，之后由 `publish` 维护（它是改完库才调的，会自行增减 total），扩展不再回源库核对。两个方向各维护自己那份。
- 已缓存条数不落 meta（它是 list 尺寸的副本，会说谎），每次读顺手 `ZCARD` 即可。

### 为什么砍掉了 head / tail / prev / next

- **`head` / `tail`（区间水位线）**：本来是用来描述「已缓存到哪儿」的，但真正取续点时是直接 `ZRANGE 0 0` / `ZREVRANGE 0 0` 从 list 首尾现读，meta 里那两份副本从没被读过——而且 list 会被 `publish` 改动，副本反而更容易过期失真。删。
- **`prev` / `next`（两端尽否）**：它是「到底」的第二个判据，但 `_isDone()` 本来就是 `count >= total` 优先，只有 `total` 偏大时才轮到它；而那种情形下「扩展推不动就收手」（上层循环的 `count <= prevCount`）同样能收敛。实测五个场景（正常到底 / 空库 / `step >` 总数 / `total` 偏小 / `total` 偏大）有无这两个标志**行为完全一致**。删。

### 为什么不再需要边界校验

- **游标模式**：带游标请求的前提就是缓存还在。三个 key 同时存在、且每次读写都续期 TTL；而游标过期是签发时刻 + 固定 TTL（不续期）。所以正常翻页路径上不会出现「游标有效而缓存已过期」。
- 即便缓存真被 `clear()` 或 TTL 抹掉，**带老游标请求也能自愈**：读窗口落在空区间 → 触发扩展，而扩展总是从该方向那一端连续往另一端生长，最终必然覆盖到游标位置（实测第 2 页仍返回正确的 `desc[5..10]`，`total` 重新回源库统计）。代价只是多一两次扩展查询。
- **页模式**：没有游标，缓存失效就从头重建，再逐步扩展到目标页；配合最大深度上限（`MAX_PAGE_DEPTH`）。扩展量按目标深度放大（`min(max(step × extendFactor, depth), extendMax)`，见下节），深翻页也不至于一轮一轮铺过去。

## 具体实现

### 类 UserPaginatorCache

对外暴露 `UserPaginatorCache` 类，以及配套的 `PaginationError`、`decodeCursor`、`redis`、`defaults`。

#### Redis 客户端

客户端在**模块内创建单例**（`ioredis`），地址取 `REDIS_URL` 环境变量（缺省 `redis://127.0.0.1:6379/0`）。所有实例与静态方法（`publish` / `clear`）共用同一个连接，**构造函数不再接收 `redis`**：

```js
const REDIS_URL = process.env.REDIS_URL || 'redis://127.0.0.1:6379/0';
const redis = new Redis(REDIS_URL, { lazyConnect: true, maxRetriesPerRequest: 2 });
redis.on('error', () => {}); // 连接级错误由各方法的 guard 包成 1500，这里吞掉避免 unhandled
```

- `lazyConnect: true`：只被 `require`（例如形状测试）时不真连，首次发命令才建连接。
- 客户端一并导出，业务侧要 flush / 查 TTL 可直接用。

#### 构造函数

```js
constructor({ model, key, where = {}, types = 'all', fields = ['type'],
              size = 15, step = 200, extendFactor = 3, extendMax = 1000,
              ttl = 1800, rev = true, now = Date.now })
```

| 参数            | 含义                                                            | 缺省       |
| --------------- | --------------------------------------------------------------- | ---------- |
| `model`         | Mongo 集合对象，契约见下                                        | 必填       |
| `key`           | key 前缀，**最后一段必须是分数字段名**                          | 必填       |
| `where`         | 业务过滤条件（uid 等）                                          | `{}`       |
| `types`         | 类型组合，`'all'` 或类型名数组                                  | `'all'`    |
| `fields`        | `[fieldType, fieldId]`，**一般只需传一个**（id 默认 `_id`）     | `['type']` |
| `size`          | 页大小缺省值                                                    | 15         |
| `step`          | 扩展条数的基准值（实际取 `step × extendFactor`）                | 200        |
| `extendFactor`  | 读路径一次扩展的倍数（`_extendSize()` 的基数）                  | 3          |
| `extendMax`     | page 深翻时一次扩展的条数上限                                   | 1000       |
| `ttl`           | 三键的 TTL（秒）                                                | 1800       |
| `rev`           | 排序方向，`true` 降序 / `false` 升序                            | `true`     |
| `now`           | 时钟注入（测试用）                                              | `Date.now` |

> **`rev` 在构造函数里**：一个实例只服务一个方向，实例内每次读写都按它派生 key。分页方法（`paginate()` / `cursor()` / `page()`）**不收方向参数**，游标也**不带方向**；要降序 + 升序两种排序，就按同一个 `key` 建两个实例（各持自己的 `desc` / `asc` 缓存，共用一份反向索引）。

构造函数内部只做配置归一化，派生出一系列 key 与排序规格，存入 `this.opts`：

- `fieldScore`：从 `key` 最后一段解出（`key.slice(key.lastIndexOf(':') + 1)`）。
- `fields` 按位置解构为 `fieldType` / `fieldId`（`fieldId` 缺省 `_id`）。
- `combo`：`types === 'all' ? 'all' : [].concat(types).slice().sort().join('_')`。
- `rev`：`Boolean(rev)` 存进 `opts`；`_keys()` / `_sort()` / `_buildFilter()` 都从它取方向。
- `keyIdx`：`${key}:idx`（与方向无关，两个方向共用一份反向索引）。
- `_sort()`：`{ [fieldScore]: rev ? -1 : 1, [fieldId]: rev ? -1 : 1 }`（Mongo 规格）。
- 当 `types !== 'all'` 时，把 `{ [fieldType]: { $in: types } }` 并进查询条件。
- **`_id` 不做类型转换**：源库 `_id` 都是字符串，keyset 直接用 member 反解出的字符串比较即可。

**model 契约**（MongoDB / mongoose）：

- `model.find(filter).sort(sort).limit(n).lean()` → 记录数组（mongoose Query 本身 thenable，不用 `.exec()`）；扩展时的 keyset 续点也拼在 `filter` 里。
- `model.countDocuments(filter)` → 数字。
- `filter` 里的 score 字段给 **Date**（`new Date(ms)`），Mongo 才能按时间比；business `where` 与生成的 keyset 条件用 `$and` 合并，避免把 `where` 里已有的同名字段顶掉。

#### 私有方法 keys

按**实例方向**（构造时的 `rev`）派生这一份缓存要用的 key（方向进 key 的落点就是这里）：

```js
_keys()
// 返回 { dir, entry, keyList, keyMeta, keyIdx }
//   dir     'desc' | 'asc'（由 this.opts.rev 决定）
//   entry   `${combo}:${dir}`（反向索引成员）
//   keyList `${key}:${combo}:${dir}:list`
//   keyMeta `${key}:${combo}:${dir}:meta`
//   keyIdx  `${key}:idx`
```

实例的所有读写都先取 `this._keys()`；同一个 `key` 上建的 desc 实例与 asc 实例因此天然走两套互不干扰的区间。

#### 公开方法 paginate

统一分页入口。**两个基础值，不用对象参数**，与 `cursor()` / `page()` 同风格。

```js
async paginate(locator = null, size = this.opts.size)
// 返回 { list, next, total }
```

- `locator` 是游标字符串（内部会 `decodeCursor`）或解码后的游标对象 → 走 `cursor(cur, size)`。
- `locator` 是数字 → 走 `page(页码, size)`（页模式）。
- `locator` 是 `null` / `undefined` → 走 `page(1, size)`（第 1 页）。
- 排序方向不在这里：用哪个方向的实例由调用方决定。
- 返回 `{ list, next, total }`：`list` 是 `{ id, type, score, member }[]`，`next` 是待交付的游标字符串（到底为 `null`），`total` 是源库条数。

#### 公开方法 cursor

游标分页：读 → 不足则扩 → 重读，直到取满一页或确认到底。

```js
async cursor(cur, size = this.opts.size)
// 返回 { list, next, total }
```

内部循环：

1. `_read(cur, size, 0, true)`：读 `size+1` 条；不足且未到底时**由 `_read()` 自己**完成一次 `_extend()`（缺省一次扩 `step × extendFactor` 条，游标模式不按深度放大）。
2. 取满（`items.length > size`）→ 收尾返回，签出 `next` 游标。
3. 取不满且已到底（`count >= total`）→ 收尾，`next = null`。
4. 取不满且未到底 → 回到 1；`ZCARD` 没推进就停（返回已有数据，不谎报到底）。

同分 band：读窗口恒从 offset 0 读起，按 **member 字典序**过滤已交付前缀，**不用 offset 跳过**（前缀被删后计数会右移导致漏读）；窗口不够时 2 倍放大，上限 `MAX_SCORE_BAND`。

#### 公开方法 page

页模式：与 cursor 同构，只是取数带 offset，覆盖目标是 `depth`。

```js
async page(page = 1, size = this.opts.size)
// 返回 { list, next, total }
```

内部逻辑：

1. `offset = (page - 1) * size`；`offset + size` 超过 `MAX_PAGE_DEPTH` 时抛深度超限，提示改用游标。
2. `depth = offset + size + 1`（要读到第 depth 条，缓存至少覆盖到这里）；同时算出本次扩展量 `extendLimit = _extendSize(depth)`。
3. 循环：`_read(null, size, offset, true, extendLimit)`；取满或覆盖到 `depth` / 到底即返回，否则继续，`ZCARD` 没推进就停。
4. page 模式和游标模式共用同一套 `_return()`，所以**同样会签 `next`**（当页不是最后一页时）：`next` 指向第 `offset+size+1` 条，可以拿来无缝升级成游标分页，不必再按页码翻。

#### 私有方法 read

```js
async _read(cur, size, offset = 0, needExtend = true, extendLimit = this._extendSize())
// 返回 { items, count, total }
// items 是内部结构 [{ member, score }]，对外交付时由 _return() 转成 { id, type, score, member }
// total = -1 表示这份缓存还没建；方向取自 this.opts.rev，不再逐次传入
```

`need_extend` 默认 `true`，含义是：**读不满时自己决定要不要扩展**，而不是把「扩展」这件事丢给上层循环。

`extendLimit` 是**本次扩展向源库取多少条**，缺省 `_extendSize()`，由 `_extendSize()` 统一算：

```js
_extendSize(depth = 0) {
  const { step, extendFactor, extendMax } = this.opts;
  return Math.min(Math.max(step * extendFactor, depth), extendMax);
}
```

- 不传 `depth`（游标模式、或直接调 `_extend()`）→ `step × extendFactor`，默认 200×3 = 600 条。
- page 模式传目标深度 → `max(3×step, depth)`，最多 `extendMax`（1000）条：缓存失效要从头扩到第 N 页时，一轮就够，不用按 `step` 铺 N/step 轮。
- 把「扩多少」收敛到这一个参数，是为了少几次「查库 + 写回 + 重读」的往返；`_extend()` 本身只是按传参执行。

内部顺序：

1. `_query()`：一段 Lua 拿到「数据窗口 + ZCARD + total」（key 由 `_keys()` 取，也就是读的是该实例方向自己那份）。
2. 同分 band 过滤（按 member 字典序过滤已交付前缀），窗口被吃满且没到上限就 2 倍放大重读。
3. 取满 `size+1` → 直接返回。
4. 读不满 → 先判断**是否已追平源库总数**（`count >= total`；`total = -1` 表示还没建缓存，不算到底）。到底了**不再 `_extend()`**，直接把已有数据返回（`next = null`）。
5. 没到底且 `needExtend === true` → 调**一次** `_extend(extendLimit)`，然后**重读一次**（`needExtend = false`，保证一次 `_read()` 最多扩展一轮，`_extend()` 不会被二次调用）：
   - 重读是必须的：刚 `ZADD` 进去的行不在扩展前的快照里，图省事直接返回旧快照会在末页**少一条**（实测踩过：46 条只翻出 45 条）。
   - 是否还要继续扩，交给上层循环按 `_isDone()` / `count <= prevCount` 决定。

- 只用 score 区间命令（`ZREVRANGEBYSCORE` / `ZRANGEBYSCORE`），不用 rank 系列，也不按下标取。
- 首页全区间 `[-inf, +inf]`；有游标则按实例方向用闭区间从游标 `t` 读起（降序范围是 `[-inf, t]`，升序是 `[t, +inf]`）。

#### 私有方法 extend

从「尚未缓存的那一端」按 keyset 续点向库取 `limit` 条，原子写回该方向的 ZSET + meta。

```js
async _extend(limit = this.opts.step)
// 无返回值：还要不要继续扩，由上层循环按 count >= total / count 推不动来判断
```

- `limit` 缺省 `step`（直接调用时）；读路径由 `_read()` 传 `_extendSize()` 的返回值（3×step 或按 depth 放大）。
- 取满与否则只决定「这批够不够用」，**不再用它判断是否到底**——到底统一由 `count >= total` 判定。

内部逻辑：

1. 尾部探针：`rev ? ZRANGE keyList 0 0 WITHSCORES : ZREVRANGE keyList 0 0 WITHSCORES`，拿到 cache 那一端边界记录的 member / score 作续点（list 空则无续点，首屏直接取最新 / 最旧 `limit` 条）。`keyList` 是 `_keys().keyList`，所以降序实例扩的是降序那份区间、升序实例扩的是升序那份。
2. keyset 续点拼进 filter，**用严格比较**（续点那条已经在缓存里，再取回来只会白占额度、还可能导致「取不动」死循环）：
   - 降序向早端：`$or: [{ [scoreField]: { $lt: at } }, { [scoreField]: at, [fieldId]: { $lt: id } }]`。
   - 升序向新端：`$gt` / `$gt`。
   - `at` 用 `new Date(ms)` 转回 Date；`id` 直接用 member 反解出的字符串（源库 `_id` 是字符串）。
3. `model.find(filter).sort(this._sort()).limit(limit).lean()` 取 `limit` 条（排序规格由实例方向决定）。
4. `total`：仅在 `GET keyMeta` 为空（这个方向还没建过缓存）时 `model.countDocuments(filter)`，否则传 `''` 沿用。
5. 过滤脏数据：**按「score 能否转成合法数字」判断**，而非 truthy。`'0000-00-00 00:00:00'` 这类「truthy 但非法」的值会转成 `NaN`，`ZADD` 报 `ERR value is not a valid float`。
6. `EVALSHA` 写回：`ZADD` 新数据、`SADD {prefix}:idx ${combo}:${dir}`（**反向索引就是在这里登记的**，只读不写会让后续 `publish` 广播不到这个组合+方向）、把首次算出的 `total` 写进 meta，三键续期。`meta` 存在时传空串沿用旧值（`publish` 会自行增减），不会覆盖。

**已知 bug 记录**：时间字段是 `'0000-00-00 00:00:00'`（老 MySQL 零日期遗留脏数据）时，`new Date('0000-00-00 00:00:00').getTime()` 得到 `NaN`，`String(NaN) === 'NaN'`，`ZADD key 'NaN' member` 会被 Redis 拒绝，报 `ERR value is not a valid float`。过滤若只写 `filter(r => r[scoreField])` 拦不住它（零日期是 truthy），必须写成 `filter(r => !Number.isNaN(this._ms(r[scoreField])))`。

#### 私有方法 return

收尾：切掉探察项、按需签游标。

```js
_return(cur, items, size, total)
// 返回 { list, next, total }
```

- `next`：取满 `size+1` 才签发，否则为 `null`。
- `list`：`items.slice(0, size)`，每项转成 `{ id, type, score, member }`（`id` / `type` 由 member 按下划线反解）。

### 游标

`base64url({ t, m?, o?, e? })`

- `t = items[size].score`（探察项，下一条待交付记录的 score），下一页闭区间从 t 读起。
- `m` / `o` 仅当页边界落在同分 band 内（`probe.score === anchor.score`）时携带：`m` 是探察项 member，`o` 是该 band 内已交付成员累计数。
- `e` 是签发时刻 + ttl（毫秒），可选：缺省不做过期校验，带了才校验（过期抛 1403）。
- **不带方向**：两个方向各有自己的 key，续读用哪份缓存完全由「请求侧选中的实例」决定，游标里再存一份方向只会多一处要校验的状态。代价是同一个游标喂给另一个方向的实例会读到另一份区间（不再是硬错误）——调用方按请求里的 `sort` 参数挑实例即可，两边本就不该混用同一个游标。
- 编码在类内、解码在类外：`decodeCursor(raw, now)` 导出，类只接受 `{ t, m?, o? }`。

### 脚本缓存 scriptLoad

为减少每次 `EVAL` 上传脚本正文的开销，用 `SCRIPT LOAD` 预编译脚本并缓存其 SHA1：

- 首次执行某段 Lua 前，先 `SCRIPT LOAD` 拿到 `sha1`，缓存在内存里。
- 之后用 `EVALSHA sha1` 执行，命中缓存就不用重复上传脚本。
- 执行时若 `EVALSHA` 报 `NOSCRIPT`（脚本缓存已失效，如 Redis 重启 / 脚本被 `SCRIPT FLUSH`），回退到 `EVAL`（重新上传正文）并再次 `SCRIPT LOAD` 刷新缓存。

实现为一个内部辅助函数 `runScript(scriptText, keys, argv)`（内部直接用模块级 `redis`）：先 `SCRIPT LOAD`（SHA 缓存在**模块级** Map，多个实例共用），执行用 `EVALSHA`；报 `NOSCRIPT` 时重新 `SCRIPT LOAD` 刷新 SHA 再 `EVALSHA`；其余异常统一包成 1500。

### 写入侧 publish

新增 / 删除一批记录时，广播到该前缀下所有已建缓存的「组合 + 方向」。

**索引只有一份（`{prefix}:idx`），list / meta 才有两份**：索引成员是 `${combo}:${dir}`，`publish` 只收 prefix，遍历索引成员、每个成员各落自己那组 list / meta，所以**一次调用就同时维护两个方向**。这是必须的——写入侧无法预知之后会被哪个方向读到，只维护一边必然出现「降序看得见、升序看不见」；若索引也按方向拆开，业务就得为同一批数据调两次 `publish`。没被读过的方向不在索引里，自然跳过；成员在索引里但它的 `meta` 已过期（脚本返回 -1），只摘掉那一个成员，不影响另一个方向。

```js
static async publish(key, action = 1, members = [], ttl = 1800)
// 返回 { changed: string[], stale: string[] }  元素形如 'all:desc' / 'article_ticker:asc'
```

- `key`：prefix，如 `user:v6:user:{uuid}:history:subscribe:act_time`。
- `action`：`1` = 新增（`ZADD`），`0` = 删除（`ZREM`）。
- `members`：`{ member, score }[]`；`add` 时 `score` 必填（ZADD 靠它定序），`del` 时也可直接给 member 字符串数组（`score` 用不上）。
- `ttl`：三键 TTL（秒）。参数就是这四个位置值，不做对象聚合。
- 从反向索引 `SMEMBERS {prefix}:idx` 取候选成员 `${combo}:${dir}`，逐个处理。
- 每个成员按 `member` 后缀的类型筛选：`all` 通吃，否则只收类型在组合名里的那些；筛完为空则跳过。
- 每个成员走一段 Lua：`meta` 不存在则返回 -1（未受理）；否则 `ZADD` / `ZREM`，并把 meta 里那个整数按真实变更条数增减（`add` 按 ZADD 新增数 `+n`，`del` 按操作条数 `-#members`，下限 0）。
- **反向索引的维护**：`-1`（这份缓存已过期）→ `SREM {prefix}:idx ${combo}:${dir}`，是唯一允许摘除索引的点；`>0` 记入 `changed`。**删空不摘索引**——空组合继续留在索引里，之后的新增才能 `ZADD` 回来（否则删空后新增进不了 list，列表会一直空到 TTL 过期）。

### 关注场景：业务自己调两次 publish

一次关注 / 取关要落两个 key（A 的订阅列表、B 的粉丝列表），两者 hash tag slot 不同，**不能塞进同一段 Lua**，由业务串起来调两次 `publish`：

```js
const [sub, fans] = await Promise.all([
  UserPaginatorCache.publish(keySubscribe, 1, [{ member: `${subRow._id}_${bType}`, score: at }]),
  UserPaginatorCache.publish(keyFans, 1, [{ member: `${fanRow._id}_${aType}`, score: at }]),
]);
```

| 落点        | 写入的 member            |
| ----------- | ------------------------ |
| A 的订阅列表 | `${订阅行 id}_${B.type}` |
| B 的粉丝列表 | `${粉丝行 id}_${A.type}` |

- prefix 由调用方按命名规范拼好传进来，类本身不拼业务 key（避免把命名规则焊死在库里）。
- 取关同样两次调用，`action` 传 `0`，`members` 只给 member 字符串即可。
- 每个 key 下若有降序 / 升序两份缓存，各自都会被更新（索引成员分方向）。

### 清空 clear

```js
static async clear(key)
// 返回清掉的「组合 + 方向」数
```

从反向索引取全部成员，按 `${combo}:${dir}` 反解出各自的 list / meta 并删掉（两个方向一起清），最后删索引本身，等于回到冷启动。用于数据整体失效（清空历史、账号注销）。

### 常量与错误码

| 项               | 值    | 说明                                       |
| ---------------- | ----- | ------------------------------------------ |
| `size`           | 15    | 页大小                                     |
| `step`           | 200   | 扩展条数基准值，必须 ≥ 2                   |
| `EXTEND_FACTOR`  | 3     | 读路径一次扩 `step × 该值` 条             |
| `EXTEND_MAX`     | 1000  | page 深翻时一次扩展的条数上限              |
| `ttl`            | 1800  | 三键同值，读 / 扩展 / 写入都续期           |
| `MAX_SCORE_BAND` | 800   | 同分 band 窗口放大上限                     |
| `MAX_PAGE_DEPTH` | 10000 | page 模式深度上限                          |

| 码   | 含义                                         |
| ---- | -------------------------------------------- |
| 1400 | 参数不合法                                   |
| 1401 | page 翻页深度超限，请改用游标                |
| 1402 | 游标非法（格式错 / 不是合法游标）             |
| 1403 | 游标已过期（仅当游标带了 e）                 |
| 1404 | 缓存构建中，请稍后重试（并发建缓存抢锁失败）—— 暂未使用：`ZADD` 幂等，不抢锁 |
| 1500 | 源库 / Redis 异常                            |

## 结束判定

- **到底** = 已缓存条数追平源库总数：`count >= total`（`total = -1` 表示这份缓存还没建，不算到底）。
- 读不满一页时先看这个条件：到底了就不扩展，直接返回 `next = null`；`_extend(extendLimit)` 之后必定重读一次（见 `_read()` 第 5 步）。
- 一次扩展取多少条由 `extendLimit` 决定：缺省 `step × 3`，page 模式按目标深度放大并封顶 1000 条 —— 减少「查库 + 写回 + 重读」的往返轮数，与「是否到底」无关（到底只看 `count >= total`）。
- **扩展推不动**（`ZCARD` 没变）时返回已有数据，不谎报到底——唯一成因是「库多了行但没 publish」，靠 TTL 过期重建收敛。
- meta 不存水位线与两端标志：续点直接读 list 首尾（比副本准），到底只用 `count >= total` 一条判据（实测有 / 无 `prev`、`next` 行为一致）。
- **方向隔离**：一个实例固定一个方向（构造时的 `rev`），`desc` 与 `asc` 各有自己的 list / meta，各自从自己的起点端往另一端生长，两个实例交替请求不会互相污染，也不会出现「区间被撕成两段」的空洞。
- 并发：多个请求同时冷启动同一个「组合 × 方向」时，各自读库、各自 `ZADD`，`ZADD` 幂等 + keyset 严格比较使结果收敛，不需要抢锁，所以错误码 1404 暂时用不上。
