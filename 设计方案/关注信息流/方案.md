# 关注信息流缓存 · 设计方案

> 关注页时间线：给「用户关注的多账号」提供一个按发布时间倒序、可分页的低延迟读取。
> 本方案聚焦**读路径（合并分页）+ 写路径（发布裁剪热点）**，关注关系本身由「用户缓存方案」提供（上限沿用产品约束 1000）。

---

## 1. 先回答三个问题（业界怎么做）

### 1.1 B 站 / 知乎 / 微博 / Twitter 这类大厂怎么实现关注信息流

统一结论：**推拉结合（hybrid）是大型社交产品的标配**，纯推（写扩散）或纯拉（读扩散）在极端规模都撑不住。这条结论有明确的一手来源支撑——Twitter 的 Timeline Service（Krikorian 2013、Yao Yue 2014 公开演讲）与 Instagram 工程博客都讲清了「按粉丝量级分层、读时合并两条路径」的做法。

- **推模式（写扩散 / Fan-out-on-Write）**：作者发帖时把 `postId` 写入每个粉丝的收件箱 ZSet（`inbox:{uid}`，score=发布时间戳）。粉丝读 = 1 次 `ZRANGE`，极快。代价是**写放大**——大 V 一条帖要写几百万次。
- **拉模式（读扩散 / Fan-out-on-Read）**：作者只写自己的发件箱（`outbox:{authorId}`）。粉丝读时实时去每个关注对象的 outbox 拉「最近 N 条」，在应用层 merge 排序。写极轻；代价是**读放大**——关注 1000 人就要合并 1000 个列表。
- **推拉结合**：普通 / 小作者用推（粉丝可控，扇出便宜），大 V / 明星用拉（粉丝几百万，推不起），读时把两份合并。代表：
  - **Twitter / X、Instagram**：非 celebrity 走推、celebrity 走拉。**注意「阈值」不是固定值**——公开资料里从 1 万到 100 万都有人提，它是按写放大成本 vs 读延迟预算调出来的经验值，大系统往往还分多档（普通推 / 大号限量推 / 明星纯拉）。
  - **微博 / 知乎（公开博文领域的常见描述）**：大 V「在线推、离线拉」，每个用户维护 `outbox`（自己发的）+ `inbox`（feed），score=发布时间戳(毫秒)，value=postId。

> ⚠️ **资料来源说明（重要）**：本节「业界做法」的依据是 Twitter / Instagram 的公开工程分享与系统设计的共识性结论。**B 站等产品的内部 feed 架构没有找到权威一手来源**（公开可查的只有压测 / 稳定性保障类文章，没有推拉架构的官方披露），故本文不再以 B 站具体数字（如「outbox 读放大 CPU 95%+」）作为论据——那类带具体数字的说法多出自 CSDN 等二手转载，可信度无法验证，请勿当作定论。本方案的设计本身不依赖任何特定大厂的未公开实现。

### 1.2 全量动态缓存列表有过期时间吗？多久？

**有，但大厂不会存「真正无限的全量」——缓存只存「最近一段时间的窗口」**，完整历史永远在 DB。

- **每用户收件箱 `inbox`**：公开博文给的是 **TTL 3~7 天** + 容量上限（500~1000 条），更旧的翻页回源 DB。理由：「很少有人翻三天前的关注流」，命中率优先、允许分钟级延迟。
- **作者发件箱 `outbox`（你说的全量列表）**：同样思路——缓存只存最近窗口（带 TTL 或按容量裁剪），完整历史在 `posts` 表（按 `creatorId + publishAt` 建索引）。outbox 设 TTL 还能顺便淘汰冷作者、回收内存。
- **关键认知**：你说的「全量缓存列表」在生产里其实是「最近 N 条的缓存窗口」；真·全量在库里，翻到深处才查。

### 1.3 关注多个账号后，是 redis 临时并集（ZUNIONSTORE）吗？

**不是实时 `ZUNIONSTORE` 并集。** 两种真实做法：

- **纯拉（本方案方向）**：读请求里对每个关注作者的 `author:feed` 取「最近 30 天」窗口，在**应用层做多路归并**（`merge-sort`），再分页。没有「并集」这个 Redis 命令参与，也没有临时 key。关注 1000 人 = 1000 次小 `ZRANGEBYSCORE` + 一次内存排序。
- **推拉结合**：普通作者的帖已经**预先并进了粉丝 inbox**（写作时异步 fan-out），读 = 1 次 `ZRANGE`；**只有大 V** 才在请求时并发去拉他们的 `outbox` 做 merge。这里的「并」发生在**写时**（异步把作者帖并入粉丝 inbox），不是每次读实时做。
- **为什么不实时 `ZUNIONSTORE`**：把 1000 个 ZSet 实时合并成一个临时 key，要写 1000 个集合、占内存、用完还得清，且每次刷新都重算。读取路径上它比应用层 merge 还慢（实时并集 = 写放大 + 重算，两头都亏）。

## 2. 本方案：纯拉模式 + 每作者发布列表（按 30 天时间窗口归并）

适配前提：**关注上限 1000**、大多数只看前面、服务端只做时间线、未读由客户端控制。

### 2.1 数据模型

| Key | 结构 | 内容 | TTL / 淘汰 |
|---|---|---|---|
| `author:feed:{authorId}` | ZSet（`member=postId`, `score=publishAt` 毫秒） | 作者发布列表（缓存保留最近 `FEED_KEEP` 条，缺省 1000；**软性数量上限**，超出回源 DB） | 双约束：① `FEED_TTL`（≥30 天，覆盖归并窗口）回收冷作者；② `FEED_KEEP` 软上限（`ZREMRANGEBYRANK` 保留最近 K 条）封死高产作者膨胀；keyset 深翻超缓存部分回源 DB |
| `post:{postId}` | **String(JSON)** | 动态详情 | Cache Aside：发布写、改时 `DEL`，下次读回源；TTL + DB 兜底 |

> **不分 inbox / outbox**：本方案不引入推模式，只有「作者维度的发布列表」`author:feed`。粉丝读时去每个关注作者的 `author:feed` 拉「最近 30 天」窗口，再应用层多路归并。没有 `inbox`（粉丝收件箱）、没有 fan-out 写扩散。
>
> **热点列表不要**：用户决策——原先的 `author:hot`（时间窗口热点列表）可以不要。`author:feed` 本身覆盖 30 天（缓存窗口 ≥30 天），归并时直接按时间下界取即可，无需再复制一份热点列表。
>
> **「缓存软上限」与「无限制分页」不矛盾，三个概念要分清**：① `author:feed` 引入**软性数量上限 `FEED_KEEP`（缺省 1000）**——发布后 `ZREMRANGEBYRANK` 保留最近 K 条，封死高产作者 ZSet 无序膨胀（评审 §6.1）。② 分页 API 仍**支持无限制 keyset 深翻**——只是超 `FEED_KEEP`（及超 `FEED_TTL` 的冷作者）的部分回源 DB 按 `creatorId + publishAt` 取，功能上「无限制分页」不变，只是不全在缓存里。③ 关注流**归并时按时间过滤取最近 30 天**（`ZREVRANGEBYSCORE since`）——这是「按时间取 30 天内的 id」。三者独立：缓存有软上限（内存安全）、分页可无限（DB 兜底）、归并截 30 天（时间窗口）。

### 2.2 发布写路径

```js
const FEED_TTL = 30 * 86400   // 作者发布列表缓存窗口：≥30 天（覆盖归并窗口；可更大如 90 天）
const FEED_KEEP = 1000        // 软性数量上限：每个作者最多缓存最近 1000 条，超出回源 DB

// 发布：写 author:feed（幂等，postId 唯一）+ 软上限裁剪 + 顺手续期
await redis.zadd(`author:feed:${a}`, publishAt, postId)
await redis.zremrangebyrank(`author:feed:${a}`, 0, -FEED_KEEP - 1)  // 保留最近 FEED_KEEP 条，超出即裁
await redis.expire(`author:feed:${a}`, FEED_TTL)                     // 顺手续期（缓存窗口，淘汰冷作者）
// 详情走 Cache Aside：post:{id} 是 String，发布用 DEL，下次读回源（发布频繁场景比 HSET 单字段简单，无并发覆盖）
```

```js
// 删除动态：feed ZREM + 详情 DEL（软上限裁剪是异步的，删帖即时生效）
await redis.zrem(`author:feed:${a}`, postId)
await redis.del(`post:${postId}`)
```

> **软上限 `FEED_KEEP` 用 `ZREMRANGEBYRANK` 兜底**（评审 §6.1）：封死高产作者 ZSet 无序膨胀。高产作者（如 20 条/天 → 30 天 600 条，仍在 1000 内）完全覆盖 30 天窗口；只有极端高产（>~33 条/天）才会在 30 天内被裁，被裁部分纯靠 DB 深翻兜底。内存同时靠 `FEED_TTL` 回收冷作者；深翻超过 `FEED_KEEP` / `FEED_TTL` 的部分回源 DB。

### 2.3 读路径（合并分页）

```js
const MERGE_WINDOW = 30 * 86400   // 归并窗口：最近 30 天（时间过滤，非数量上限）
const CANDIDATE_CAP = 50          // 每个作者单次最多取多少候选（限制回包体积 + 归并 CPU，见评审 §6.2）
const follows = await getFollowIds(uid)          // 来自用户缓存方案，≤ 1000
const since = now - MERGE_WINDOW
// 单次 pipeline 把全部 ≤1000 个作者的「最近 30 天 + 每作者最多 CANDIDATE_CAP 条」一次取齐（1 RTT）
// ZREVRANGEBYSCORE 取最高分（最新）在前，LIMIT 0 CANDIDATE_CAP 封顶单作者回包
const cmds = follows.map(a => ['ZREVRANGEBYSCORE', `author:feed:${a}`, '+inf', String(since), 'WITHSCORES', 'LIMIT', 0, CANDIDATE_CAP])
const batches = await pipeline(cmds)              // 1 次网络往返；命令数 = 关注数 ≤1000，在 pipeline 上限内（连接池需足够，见 §6.2）
const candidates = flatten(batches).filter(r => r.length)   // 冷作者（30 天内无帖）返回空数组，自动跳过
// 多路归并：publishAt 倒序、postId 去重（归并窗口 = 30 天）
const merged = mergeSortDescDedup(candidates)
// 分页：游标 (lastPublishAt, lastPostId) 取本页 N 条；只对最终 N 个取详情
const page = paginateByCursor(merged, cursor, N)
return await mgetDetails(page.map(m => m.postId))
```

- **单次 pipeline 取齐（1 RTT）**：取代原「分 5 段、每段一个 pipeline」；命令数 = 关注数（≤1000）在 pipeline 上限内，但需保证 Redis 连接池与单 pipeline 命令数上限，避免队列阻塞（评审 §6.2）。
- **`CANDIDATE_CAP` 封顶回包**：`ZREVRANGEBYSCORE ... LIMIT 0 CANDIDATE_CAP` 把每个作者回包压到 ≤50 条，候选总量从上不封顶降到 ≤ 关注数 × 50，显著降低 Redis→应用层带宽与应用层归并/去重 CPU；冷作者空结果零 CPU（优化点 2）。代价见 §6.2（极深页可选放大 `CANDIDATE_CAP` 或按作者回源 DB）。
- **归并窗口 = 30 天（时间过滤）**：只取 `publishAt ≥ now-30d` 的 id，对应「多路并归时按时间取 30 天内的 id」。翻到 30 天前即止。
- **深翻（游标翻页）**：用 keyset 游标 `(lastPublishAt, lastPostId)` 在合并结果上取值，无需重算整段；作者自己的主页深翻（超 `FEED_KEEP` / 超 `FEED_TTL` 的冷作者）回源 DB 按 `creatorId + publishAt` keyset 取。
- **没有 3000 数量上限**：关注流以「30 天时间窗口」为界，不按条数封顶（§2.1 已说明三个概念的区别）。

### 2.4 游标分页

- `(lastPublishAt, lastPostId)` 二元组：同毫秒用 `postId` 兜底（id 趋势与时间一致，或显式带单调序号）。避免 `OFFSET` 深翻的数据跳动与性能问题。keyset 游标天然支持「无限制分页」。

### 2.5 未来扩展：资源类型过滤 / 热点排序（当前阶段先不做）

当前阶段只按时间线排序、不过滤（用户决策）。两项扩展的预留设计见下，待后续要做时再落地：

- **按资源类型过滤（如只看视频）**：过滤需要每条动态的 `type`（视频/图文/…）。ZSet 里只有 `postId`，所以不能在归并前用 `type` 裁。两种做法：
  1. **归并后过滤（简单，初期）**：先按时间归并截到 `N × k` 候选，取详情后按 `type` 过滤，再补满 N。代价：候选要多取一些（`k` 倍）才能填满一页。
  2. **type 冗余进索引（高效）**：`author:feed` 的 member 编码成 `postId`，或另建 `author:feed:{type}:{id}` 分类型窗口；发布时按 type 写对应窗口。读时只拉目标 type 的窗口，零浪费。推荐等真要支持多类型时再上。
- **按热点排序**：热点分要近实时聚合（点赞/评论/转发/曝光）。做法：消费行为事件（Kafka）增量算 `hotScore` 写入 `post:{id}` 详情或独立 `post:hot:{id}`；归并阶段按 `(hotScore, publishAt)` 排序。注意热点排序会让游标变 `(lastHotScore, lastPostId)`，且与时间线游标不互通，建议作为独立 `sort=hot` 入口，不混进时间线。

### 2.6 热点作者 L1 本地缓存（优化点 3，见评审 §6.3）

纯拉模式下，头部大 V 的 `author:feed` 被成千上万粉丝并发拉，其所在 Redis 分片成单点（评审 §6.3 问题 3）。大 V 的 feed 内容变化频率远低于被读频率，适合在应用进程内存加一层短 TTL 的 L1 缓存：

- **缓存对象**：大 V / 热点作者的「最近 30 天 feed 列表」（`postId + publishAt` 数组），按 `author:feed:{id}` 为 key。
- **TTL**：5~10 秒（短，因为内容会变；10 秒内作者再发帖，最多延迟 10 秒出现在粉丝流，可接受）。
- **命中即短路**：粉丝读路径打 Redis 前先查 L1，命中直接返回该作者候选，省掉 `ZREVRANGEBYSCORE`。
- **失效**：作者发布时 `DEL` 对应 L1 条目（或等 TTL 自然过期）；发布频率低，`DEL` 成本低。
- **如何识别热点作者**：按粉丝量级阈值（如粉丝 > 1 万）或按 L1 命中率自适应；只缓存「高粉丝重叠度」作者，避免普通作者占进程内存。

收益：一个千万粉丝大 V 的 feed 一次 Redis 读被 L1 挡掉绝大部分，其分片 QPS 从「粉丝并发数」降到「每 5~10 秒几次」，单点风险基本消解。普通作者不走 L1，仍走 Redis（它们的并发本就分散）。

## 3. 降级与回源

- `author:feed` miss（缓存窗口 `FEED_TTL` 过期 / 冷作者） → 回源 DB：`posts` 按 `creatorId + publishAt` 取最近 30 天（深翻则按 keyset `publishAt < cursor` 取 next chunk）。超 `FEED_KEEP` 被缓存裁掉的旧帖同样回源 DB（缓存软上限只保内存，不丢数据）。
- `post:{id}` miss → 回源 DB 详情。
- 缓存只负责「快」，不是 source of truth；DB 永远兜底（包括 30 天窗口内的数据，若某作者 `author:feed` 缓存缺失也不影响正确性）。
- 极端：关注数触到产品上限（1000）仍走完整归并；超过才降级（按发布时间取前 N）。

## 4. 演进（当前阶段：纯拉，不引入推）

**当前阶段明确只做纯拉（读扩散）**，不引入 `inbox` / fan-out 推模式（用户决策）。纯拉在「关注上限 1000、大多只看前面、作者发布频率低」时最优（简单、无写放大）。出现以下信号再升级：

1. **平均关注数上升 → 读放大**（归并 1000 个列表变慢）：给**活跃小作者**加推，把他们的新帖预先并到粉丝 `inbox`（异步 fan-out）。
2. **出现大 V（粉丝量远超阈值）**：保持拉（正是现在的设计），大 V 的 `author:feed` 被很多粉丝并发拉，加本地缓存 + 热点隔离（参考业界对热点账号的缓存隔离做法）。
3. **阈值经验值（业界）**：Twitter 25k、微博 / 抖音按粉丝量级分层。你的场景关注上限才 1000、且大多看前面，**可能长期不需要推**。

## 5. 决策记录（已确认）

1. **不分 inbox / outbox**：不引入推模式，只有「作者维度的发布列表」`author:feed`；粉丝读时去每个关注作者的 `author:feed` 拉窗口再应用层归并。
2. **不要热点列表**：原 `author:hot`（时间窗口热点列表）去掉，`author:feed` 本身覆盖 30 天窗口，归并时直接按时间下界取即可。
3. **`author:feed` 引入软性数量上限 `FEED_KEEP`（缺省 1000）**：原「无限制分页 / 不按数量裁剪」改为——缓存保留最近 K 条（`ZREMRANGEBYRANK`），封死高产作者 ZSet 膨胀（评审 §6.1）；分页 API 仍无限制，超 K 部分回源 DB keyset 深翻。
4. **归并窗口 = 30 天（时间过滤）**：多路并归时只取每个作者 `author:feed` 中 `publishAt ≥ now-30d` 的 id；以时间窗口为界，不按条数封顶（原 3000 数量上限取消）。
5. **关注上限 = 1000**：读路径规模依赖此值。
6. **详情缓存 = String(JSON)**：发布 / 修改用 `DEL`，下次读回源（Cache Aside），无并发覆盖。
7. **当前只按时间排序；资源类型过滤 / 热点排序先不做**（用户决策），保留为未来扩展，见 §2.5。
8. **读路径：单次 pipeline 取齐 + 单作者候选上限 `CANDIDATE_CAP`（缺省 50）**（评审 §6.2）：1 RTT 取代分段 Pipeline；`ZREVRANGEBYSCORE ... LIMIT 0 CANDIDATE_CAP` 封顶回包体积与归并 CPU；冷作者空结果自动跳过。
9. **热点作者 L1 本地缓存（5~10s TTL）**（评审 §6.3）：头部大 V 的近期 feed 缓存进应用进程内存，挡掉重复 Redis 读；发布时 `DEL` 对应条目。

## 6. 评审与优化（潜在问题 + 改进）

下面是对初稿的三处隐患评审与对应优化落地（来自方案评审）。

### 6.1 问题 1：活跃作者 ZSet 无序膨胀 → 引入软上限 FEED_KEEP
- **隐患**：原方案 `author:feed` 不按数量裁剪、只靠 TTL 回收。高产 / 专业号（如 20 条/天 → 30 天 600 条）只要每天有新动态，TTL 持续续期，ZSet Key 会不断膨胀；Redis ZSet 在元素变多时从 listpack 升级为 skiplist+dict，内存与 `ZRANGEBYSCORE` 开销显著上升，长期有撑爆单分片 / 拖慢读取的风险。
- **优化点 1（已采纳）**：发布后顺手 `ZREMRANGEBYRANK 0 -FEED_KEEP-1`，**软性数量上限**（缺省 1000）。既覆盖绝大多数 30 天窗口（1000 条 ≈ 33 条/天 × 30 天），又封死膨胀；超出的纯靠 DB 深翻兜底（§2.2 / §3）。
- **代价**：极端高产（>~33 条/天）作者在 30 天内的旧帖会被缓存裁掉，其主页深翻或粉丝流极深处会回源 DB——可接受（DB 永远兜底）。

### 6.2 问题 2：读路径回包体积 + 应用层归并 CPU → 单 pipeline 取齐 + 单作者候选上限
- **隐患**：关注 1000、其中大量近期活跃时，单次请求经 Pipeline 返回数千个 postId+score，Redis→应用层内网带宽与应用层归并/去重 CPU 在极高 QPS 下累积明显。
- **优化点 2（已采纳）**：① 把分段 Pipeline 改为**单次 pipeline 取齐全部 ≤1000 个作者**（1 RTT，命令数在 pipeline 上限内，需保证连接池充足）；② 每个作者用 `ZREVRANGEBYSCORE ... LIMIT 0 CANDIDATE_CAP`（`CANDIDATE_CAP` 缺省 50）**封顶单作者回包**，把候选总量从上不封顶压到 ≤ 关注数 × 50；③ 冷作者（30 天内无帖）返回空数组，自动跳过，零 CPU。
- **代价**：`CANDIDATE_CAP` 是启发式上限——极端情况下某作者 29 天前的帖可能不在全局 top-N 候选里，但这类帖本就不会出现在活跃 feed 的前几页；严格深翻可放大 `CANDIDATE_CAP` 或按作者回源 DB。另：单 pipeline 塞 1000 条命令需确认 Redis 连接池与单 pipeline 命令数上限，避免队列阻塞（优化点 2 原文提示）。

### 6.3 问题 3：热点作者单点冲击 → L1 本地缓存
- **隐患**：纯拉下某作者突然爆火，成千上万粉丝并发 `ZREVRANGEBYSCORE` 其 `author:feed`，该作者所在 Redis 分片成单点，CPU 飙高。
- **优化点 3（已采纳）**：头部大 V / 热点作者的「最近 30 天 feed 列表」在应用进程内存加**短 TTL（5~10 秒）L1 缓存**（§2.6）。粉丝读路径先查 L1，命中即短路，挡掉绝大部分重复 Redis 读；作者发布时 `DEL` 对应 L1 条目。按粉丝量级阈值或命中率识别热点作者，避免普通作者占进程内存。

## 7. 仍待定（开放项）

1. **`FEED_KEEP` 具体值**：500 / 1000 / 其他？权衡 30 天窗口覆盖率 vs 单作者 ZSet 内存（1000 ≈ 33 条/天 刚好覆盖 30 天）。
2. **`CANDIDATE_CAP` 取值**：50 是否够；与「全局 top-N 严格正确」的权衡（见 §6.2）。
3. **L1 缓存 TTL 与热点作者识别阈值**：5s / 10s？粉丝 > 多少算热点？或按命中率自适应。
4. **`FEED_TTL` 是否还需 ≥30 天**：有了软上限后，TTL 只负责回收冷作者；可缩到更短（如 7 天）以降低内存，深翻全靠 DB。
5. **资源类型过滤 / 热点排序的落地方式**：当前不做，两类扩展的预留设计见 §2.5（归并后过滤 vs type 冗余进索引；独立 `sort=hot` 入口）。
6. **是否仍需推模式**：出现大 V 单点（即便有 L1）仍可考虑对超大 V 走拉 + L1 双层，而非 fan-out 推（演进 §4）。
