# 最新更新列表 · 设计方案

## 1. 需求

展示「用户关注的号」的列表，规则：

- 有新动态且还没看过的（未读）排在最前；
- 其余的按最后发布时间从新到旧排；
- 未读组和已读组内部都按发布时间倒序；
- 列表长度固定为 **N**（20 / 50 之类），一次取全，**不分页**；
- 关注数上限 **1000**。

---

## 2. 一句话方案

**写侧只改作者自己那一行数据，不给粉丝写任何东西；分批读侧取关注列表 → 取每个号的最后发布时间 → 内存里比一下排个序 → 截断前 N → 所有批次取完后 → 只取这 N 个的完整详情。**

---

## 3. 数据模型

### 3.1 需要新增的两个字段

| 字段 | 加在哪张表 | 含义 | 为什么放这里 |
|---|---|---|---|
| `lastPostAt` | `users`（作者维度） | 这个号最后一次发动态的时间 | 它是「作者」的属性，一个号一份，跟有多少粉丝无关 |
| `lastReadAt` | `follows`（用户 × 关注对象） | 我最后一次点开这个号的时间 | 它是每个人自己的私有状态，只能放这里 |

### 3.2 不新增的字段

**不存 `hasUnread` 布尔。** 未读是比出来的，不是存出来的：

```
unread = (lastPostAt - lastReadAt) > READ_TOLERANCE   // READ_TOLERANCE ≈ 2000ms
```

相等、或差值落在容忍窗口内都算**已读**。窗口是为吸收「点开瞬间作者发文」的竞态（见 6.2）。

存布尔的坏处：谁来清、什么时候清、和真实状态对不上怎么办——全是麻烦。而水位线是单调的，重复上报天然幂等，出问题能重算。

### 3.3 坑：`lastReadAt` 必须初始化

建关注关系时就写 `followedAt`。

---

## 4. 读流程（两阶段取数）

### 4.1 为什么必须处理完全部 id 再截断

`unread` 是逐条比出来的，**在算完之前不知道谁未读，也就选不出 Top N**。所以顺序只能是：

```
取齐全部 id → 计算并排序 → 截断 top N → mget 详情
```

（>SCAN_LIMIT 时才退回分批截断，证明见 §8；≤SCAN_LIMIT 一次取齐即可。）

### 4.2 为什么分两阶段

既然要拿全部关注对象的 `lastPostAt`，如果顺手从「详情缓存」里读，就要反序列化几百份完整详情（头像、昵称、简介……）却只用掉 N 份。所以单独用一张**只装时间戳的轻量表**，先用很轻的数据选出 Top N，再只取这 N 个的完整详情。

**排序只依赖两个数字**——`lastPostAt`（来自 `authors:lp`）和 `lastReadAt`（来自 `follows:read:{uid}`），详情里的展示字段一个都不参与。所以「把所有详情都取回来再排序」是完全没必要的：取详情只为了最后展示那 N 条。

### 4.3 五步流程

```
① 取全部关注列表（来自用户缓存方案，≤ SCAN_LIMIT 个 id）→ followeeId 列表（+ followedAt，降级时按它倒序）
② 取「上次点开时间」Hash（一次 `HGETALL`，≤1000 字段很小）         → followeeId → lastReadAt
③ 取「作者发布时间表」（**一次 pipeline 取齐全部 id 的 lastPostAt**，按 64 片分组 `HMGET`，1 个 RTT）→ authorId → lastPostAt
④ 内存排序：未读在前 → 发布时间新的在前 → 截断出 N 个 id（容忍窗口见 3.2）
⑤ mget 这 N 个的完整详情（头像、昵称）
```

第 ⑤ 步取详情是因为第 ④ 步的结果是 N 个 id，此时才需要展示用的信息。

### 4.4 代码骨架

```js
const N = 50
const SCAN_LIMIT = 3000    // 全量算的上限；pipeline 下扫 3000 仍是 1 RTT，故从 1000 提到 3000
const READ_TOLERANCE = 2000 // 未读比较的容忍窗口（ms），吸收「点开瞬间发文」竞态，见 3.2 / 6.2

// ① 关注列表 `follows:{uid}` 由「用户缓存方案」提供，这里只消费其取 id 接口。total = 关注总数。
const total = await getFollowCount(uid)
if (total > SCAN_LIMIT) {
  // 降级（历史 / 水军把产品上限撑爆）：取最近关注的 SCAN_LIMIT 个，仍按 lastPostAt 倒序，未读一律 false。
  // 不再退化成 followedAt 倒序——至少保住内容时效，避免体验断崖（见 9 / 11.8）。
  const ids = await getFollowIds(uid, 0, SCAN_LIMIT - 1, 'desc')   // 按 followedAt 倒序取前 SCAN_LIMIT
  const times = await hmGetSharded('authors:lp', ids)             // 仍走单次 pipeline
  const rows = ids.map((id, j) => ({ id, p: Number(times[j] ?? 0), unread: 0 }))
                 .sort((a, b) => b.p - a.p || (a.id < b.id ? -1 : 1)).slice(0, N)
  return { list: await mgetDetails(rows.map(r => r.id)), degraded: true }
}

// ② 已读水位线 Hash：一次 HGETALL（≤1000 字段，很小）；miss 时跟关注列表同一次回源
const readMap = await redis.hGetAll(`follows:read:${uid}`)     // { followeeId: ms }

// ③ 一次 pipeline 取齐全部 id 的 lastPostAt：按 crc32 % 64 分组，每组一个 HMGET，pipeline 一把发出去 = 1 RTT
const ids = await getFollowIds(uid, 0, total - 1)             // total ≤ SCAN_LIMIT，一次拿全
const times = await hmGetSharded('authors:lp', ids)           // 单次 pipeline，≈64 条 HMGET，1 RTT

// ④ 内存排序：未读在前 → 发布时间新在前 → 截前 N（容忍窗口见 3.2）
const cmp = (a, b) => (b.unread - a.unread) || (b.p - a.p) || (a.id < b.id ? -1 : 1)
const rows = ids.map((id, j) => {
  const p = Number(times[j] ?? 0)
  const r = Number(readMap[id] ?? 0)
  return { id, p, unread: (p - r) > READ_TOLERANCE ? 1 : 0 }
}).sort(cmp).slice(0, N)

// ⑤ 只取这 N 个的完整详情
const details = await mgetDetails(rows.map(t => t.id))
return { list: merge(rows, details), degraded: false }
```

> 关键变化：原先「分 5 段、每段独立 pipeline」改成「**一次 pipeline 取齐全部 ≤3000 个 id**」。≤SCAN_LIMIT 时内存里同时持有的就是全部 id（最多 3000 个 `{id,p,r}`，几十 KB），完全装得下，无需分批截断。分批截断的证明见 §8，仅作 >SCAN_LIMIT 或内存吃紧时的兜底。

### 4.5 排序结果不落缓存

重算一遍的成本 = 1 次取关注列表（来自用户缓存方案）+ 1 次 `HGETALL`（已读水位线）+ **1 次 pipeline**（取齐全部 lastPostAt，1 RTT）+ 一次内存排序，关注数 ≤3000 都是**几毫秒**。

存了反而要在三处记得删它（发布、点开、取关），漏一处就是显示错的列表——**不划算**。

> 什么时候才值得存：接口 QPS 到每秒几百、且关注数超过 2000。那时只存「N 个 id」，TTL 30~60 秒，详情仍走详情缓存。

### 4.6 为什么不用 Lua 把全流程搬进 Redis（优化点 1 的取舍）

直觉做法：写一个 Lua 脚本，把「crc32 分片聚合查 lastPostAt → 算 unread → 排序截断」全在 Redis 内做完，应用端只发一次脚本调用，网络从几十次降为 1 次。**听起来很美，但有三个硬伤，本方案不采用：**

1. **Redis Cluster 下会 `CROSSSLOT`。** 脚本要碰 `authors:lp:{0..63}` 共 64 个分片 key，它们各自的 hash tag `{n}` 不同 → 落在不同 slot；再加上 `follows:read:{uid}` 又一个 slot。Cluster 要求一个 Lua 脚本里所有 key 必须在同一 slot，否则直接报错。除非把全部分片 key 和 read key 用同一个 hash tag 钉死到一个 slot（那就退化成单实例，丢了 Cluster 的水平扩展）。
2. **Redis Lua 没有 `crc32`。** 分片映射只能在应用端算完再把「按片分组」的 id 传进去，省不掉客户端那步，那「单次脚本」的收益就被削掉一半。
3. **长脚本阻塞单线程。** 1000 个 `HGET` + 排序在脚本里串行执行期间，Redis 事件循环被独占，所有其他客户端的命令都被卡住——高 QPS 下这会把尾延迟（tail latency）拉得更糟，和「降网络往返」的初衷相反。

**正解是单次 pipeline 取齐**：客户端先按 `crc32 % 64` 把 ≤3000 个 id 分组，每组一条 `HMGET`，全部塞进一个 pipeline 一次发出去 = **1 个 RTT**，服务端并行处理不阻塞，Cluster 下每条 `HMGET` 走自己分片的 slot 也不冲突。网络开销从「5 段 × 16 次（顺序则 80 RTT）」压到 **1 RTT**，且无上述三害。

## 5. Redis 缓存设计

### 5.1 Key 清单

| Key | 结构 | 内容 | TTL / 淘汰 |
|---|---|---|---|
| `follows:{uid}`（关注列表） | **由「用户缓存方案」负责**（见下文），本方案只消费其分段读接口 | 全量关注列表（id + followedAt） | 不在本文范围 |
| `follows:read:{uid}` | Hash | `followeeId → 上次点开时间(毫秒)` | **30 小时滑动**（读 / 写都续期）；miss 时跟关注列表一次回源重建；取关时 `HDEL` 单字段 |
| `authors:lp:{shard}`（`shard = crc32(id) % 64`，固定 64 片） | Hash | `authorId → 最后发布时间(毫秒)`，**全局共享** | **不设 key 级 TTL**；分片数固定 64；**清理冷字段**（`HSCAN` 按值扫，>180 天未发的 `HDEL`，见 5.6）；miss 回源 `users` |

### 5.2 为什么 `lastReadAt` 拆成独立 Hash

点开某个号是很高频的操作。如果它混在一整块 JSON 里，每次点开都要「读出来 → 改 → 写回去」，并发时会互相覆盖。拆成 Hash 后，点开只改一个字段，O(1) 且无竞态。

### 5.3 为什么用 Hash 而不是 String

- 一次 `hmGet` 只需传 1000 个 field 值；`mget` 要把 1000 个完整 key 名也传过去，多一倍传输量；
- 每个 String key 除了 key 名本身（`sds` + `robj` + dictEntry），还要在 expires 字典里多占一项，**每条 100+ 字节**；Hash 的字段只有 dictEntry + field + value。几十万作者差几十 MB，上千万就是 GB 级。
- 这条结论对「想要字段级过期」同样成立——**不用为了过期换成 String**，保持 Hash 也能做到。

### 5.4 缓存是平铺的，不是层级依赖

这几块缓存各自独立、互不依赖。不存在「一层 miss 了才查下一层」的强制顺序，哪块 miss 就单独回源重建那一块。

### 5.5 过期策略：三块缓存分别该怎么设

判断标准是**「丢了会怎样」**——能低成本回源、且丢失后的表现可接受的，才适合设 TTL；一丢就把全站显示搞错的，宁可不设 key 级 TTL。

| Key | 丢了会怎样 | 回源成本 | 结论 |
|---|---|---|---|
| `follows:{uid}`（关注列表） | 多查一次关注表 | 1 次查询 | **不在本文范围**（由用户缓存方案负责） |
| `follows:read:{uid}` | 该用户打开这个列表时**全部显示未读** | 跟关注列表同一次查询（`follows` 表本来就有 `lastReadAt`） | 中长 TTL（30 小时滑动），别长驻 |
| `authors:lp:{shard}` | **所有用户**看所有号都显示已读 | 批量回源 `users.lastPostAt` | 不设 key 级 TTL |

**`follows:read:{uid}` 要设 TTL（30 小时），且要比 `follows` 长得多。**

- 不能长驻：它是用户私有状态，上亿用户的冷号会永远留在内存里；第 7.1 节「只给活跃用户建、靠 TTL 淘汰冷的」这条前提本身就要求它有 TTL。
- 关键约束：**必须比 `follows:{uid}`（用户缓存方案，通常 6~12 小时）长**。`lastReadAt` 是「已经看到哪儿」的水位线，丢了整个列表变未读，比关注列表丢了严重得多。**取 30 小时**是个折中——活跃用户每次读写都续期，冷用户一天多后回收，回流时回源补回。
- **回源是零额外成本**：关注列表 miss 时本来就要查 `follows` 表，把 `lastReadAt` 一起 `select` 出来顺手写回 Hash 即可，别让它单独触发一次查询。
- 取关时 `HDEL follows:read:{uid} {followeeId}`。否则「取关 → 重新关注」会把取关前的已读水位线带回来，期间的新动态被误判成已读；顺带也避免 Hash 因反复关注/取关越滚越大。

**`authors:lp:{shard}` 不设 key 级 TTL，但清理冷字段。**

- 它是**全局共享**的一张表，一个分片的 key 里装着几万个作者。整 key 一过期，所有作者的 `lastPostAt` 同时变 0 → 全站所有用户的列表都判成「已读」，而且是**静默**的（用户不会意识到是缓存问题）。代价远大于收益，所以**不设 key 级 TTL**。
- **清理冷字段（HSCAN 按值扫）**：字段值就是 `lastPostAt`，**值小就是老**，无需额外索引。定时任务逐分片 `HSCAN`，把 `value < now - 180d` 的字段 `HDEL`（180 天没发动态的作者视为僵尸号）。miss 的字段回源 `users.lastPostAt` 批量 `$in` 补回。这条治理**前提是 §6.1 的 `HSET_MAX` 单调必须守住**——否则乱序事件把值改小，按值清扫就会误删活跃作者，该号对全站静默显示已读。
- 字段只在发布时更新（`HSET_MAX` 保单调，见 6.1）。
- 别指望 `allkeys-lru` 兜底：LRU 是**按整个 key** 淘汰的，淘汰一个分片等于淘汰几万作者，效果等同整 key 过期——这一条不该作为方案正确性的依赖。

### 5.6 `authors:lp` 的冷字段清理（HSCAN 按值扫）

本方案**清理冷字段**：分片数固定 64，活跃作者留在表里，僵尸作者（>180 天未发）由定时任务 `HSCAN` 按值扫掉。这个场景有个很好的性质——**字段值本身就是时间戳**，所以「这个字段有多老」不用另外记，`value < now - 180d` 即可判，**不需要再建 `ZSET` 清理队列**（省掉一份与主数据同量级的内存和「两边写不同步」的负担）。

| 做法 | 写入 | 清理 | 取舍 |
|---|---|---|---|
| **A. Hash + `HSCAN` 按值扫**（本方案） | `HSET_MAX` Lua 保单调 | 定时 `HSCAN` + `HDEL` | 内存可控、Cluster 友好、无额外索引；代价是写一个清扫任务、清理有一个周期延迟 |
| B. Hash + `HEXPIRE` | `HSET` + `HEXPIRE` | Redis 自动过期 | 零运维，但要 Redis ≥ 7.4，托管实例常只到 7.0/7.2，客户端方法名也未必有 |
| C. 换 per-author String key | `SET k v EX ttl` | key 级 TTL | 天然过期，但内存反而更多（5.3）；**Cluster 下 `MGET` 跨 slot 报 `CROSSSLOT`** |

**做法 A 的两个要点：**

1. **清扫不需辅助索引**：`HSCAN` 拿到 `field + value`，值即年龄，直接判。
2. **写入必须保单调**（§6.1 的 `HSET_MAX`）：值被乱序事件改小 → 按值清扫误删活跃作者 → 该号全站静默已读。这是清理能成立的前提。

> 之前一度定过「不删冷字段、固定 16 片」。复查后发现：作者量到千万级时单分片 40MB+ 触发大 key 告警，且僵尸作者永久驻留是缓慢内存泄漏。故改为 64 片 + 冷字段清理（见 7.2 / 11.7）。

## 6. 写路径

### 6.1 发布动态

```js
// 顺序很重要：先落库，再抬水位线
await Post.create(doc)
await User.updateOne({ _id: authorId }, { $max: { lastPostAt: doc.modified_time } })
const SHARD_COUNT = 64
await redis.eval(HSET_MAX, 1, `authors:lp:${crc32(String(authorId)) % SHARD_COUNT}`, +doc.modified_time, authorId)  // Lua 保单调，见下；也是 5.6 冷字段清理能成立的前提
await redis.del(`feed:posts:${authorId}`)     // 该号的动态列表缓存
await redis.del(`user:${authorId}`)           // 详情缓存（JSON String，发布时直接 DEL，见 11.1）
```

`HSET_MAX`（缓存侧保单调，与库里 `$max` 对齐）：

```lua
-- KEYS[1] = authors:lp:{shard}   ARGV[1] = newTs   ARGV[2] = authorId
if tonumber(ARGV[1]) > tonumber(redis.call('HGET', KEYS[1], ARGV[2]) or 0) then
  redis.call('HSET', KEYS[1], ARGV[2], ARGV[1])
end
```

- 用 **`$max` 而不是 `$set`**：发布链路里的重试、异步队列、补发历史动态，都可能让 `$set` 把水位线改小，导致已读状态整体错乱。`$max` 让它单调，免疫乱序。
- **缓存侧同样要保单调**，用上面的 `HSET_MAX` 脚本而不是裸 `HSET`——重试 / 补发历史动态这类乱序事件不会把值改小。
- **只改作者自己那一份，不给粉丝写任何东西**——O(1)，与粉丝数无关。
- 顺序反了会出现「显示有新动态，点进去空白」的假未读。

### 6.2 点开头像 / 进主页

```js
const author = await User.findById(followeeId, { lastPostAt: 1 })
const mark = author?.lastPostAt ?? +new Date()      // 取作者最新发布时间（见下，为何不取 now）
const key = `follows:read:${uid}`
// 写单字段 + 续期（滑动 TTL，30 小时没来的用户会被回收，见 5.5）
await redis.multi().hset(key, followeeId, +mark).expire(key, READ_TTL).exec()
queue.push(() => Follow.updateOne(                             // 异步批量刷库
  { uid, followeeId }, { $max: { lastReadAt: mark } }
))
```

- **记录值取 `author.lastPostAt`，不取 `now`**：`now` 会把「点开前一瞬间刚发布、但本次拉取没拿到的那条」也标成已读（静默丢一条）。`author.lastPostAt` 是「点开这一刻确定已存在的最新一条」，作为「我看到哪儿」的水位线更安全——它只标到确定存在的最新动态为止。
- **但 `lastPostAt` 治不了「点开瞬间作者又发一条」的竞态**：那条新动态 `publishAt > mark`，按裸规则会判未读，用户「刚看完又显示未读」会有 glitch。故**未读比较加容忍窗口**（§3.2）：`unread = (lastPostAt - lastReadAt) > READ_TOLERANCE`（2s）。点开前后 2s 内发的动态视为已读，吸收竞态。代价是 2s 窗口内真·新动态也被标已读——极低频、且用户下一次打开即恢复，可接受。
- （曾考虑 `max(author.lastPostAt, now)` = `now`，但它对这竞态无效：发文在点开之后，`publishAt` 仍 > `now`，照样未读。所以不采用。）
- 写量 ≈ 点开率 × DAU，用 redis 承接 + 节流（同一 `(uid, followeeId)` 60 秒内只写一次）+ 异步批量刷回。
- **是否标记已读完全由客户端决定**：客户端在合适的时机发请求，服务端只负责记录 `lastReadAt`，不做任何服务端自动判定（见 11.4）。

### 6.3 关注 / 取关

```js
// 关注列表 `follows:{uid}` 自身由「用户缓存方案」维护，本方案不负责（见 5.1 / 11）。
// 取关时只需清掉这个号的已读水位线（本方案自己的缓存）：
await redis.hdel(`follows:read:${uid}`, followeeId)
```

取关必须 `HDEL`：不清的话「取关 → 重新关注」会把取关前的 `lastReadAt` 带回来（那时它往往 ≥ `lastPostAt`），期间的新动态会被误判成已读，且不会自愈。关注时不用动 read Hash——新号在 Hash 里没有字段，本来就按「从没点开过」算未读。

### 6.4 发布写入必须收口

普通用户走用户端服务、专业号走内容管理系统，**两条链路只要有一条漏写 `lastPostAt`，这个号就对所有粉丝永远显示已读，且无法自愈**。

做法：`posts` 落库后统一发一个事件（或用 change stream），由唯一的消费者负责更新 `users.lastPostAt` 和 `authors:lp`，不要在两处业务代码里各写一遍。

- **历史数据回填**：旧 `users` 记录可能没有 `lastPostAt` 字段。用一次性脚本扫全表，按各作者 `posts` 的 `max(modified_time)` 写回 `users.lastPostAt`（缓存侧随之由发布事件补）。读路径对取不到的 `lastPostAt` 按 `null/0` 处理，归入已读组（见 9 / 11.5）。

## 7. 容量与分片

### 7.1 用户维度的数据：不用人工分片

一个用户一个 key，redis Cluster 会自动按 key 名把它们撒到不同节点。**上亿用户就是上亿个小 key，这是 redis 最擅长的场景。**

但**不可能给所有用户都建缓存**——只给活跃用户建，靠 TTL 自动淘汰冷的。

```
1 万 DAU × (关注列表 ~40KB + 点开时间 ~几KB) ≈ 几百 MB
```

### 7.2 全局作者表：必须人工分片

它是**一个** key，redis 里单个 key 只能落在一个节点上。所以必须按作者数切开：

```js
const SHARD_COUNT = 64
const shard = id => crc32(String(id)) % SHARD_COUNT
// 读：按片分组后塞进同一个 pipeline，一次发出去 = 1 RTT（见 4.4 / 4.6）
```

本方案**分片数固定 64**（由全局作者量、单分片内存、大 key 告警阈值权衡后定，见 11.7），并清理冷字段（见 5.5 / 5.6）：

- **为什么从 16 提到 64**：作者量到千万级时，16 片的单分片 ≈ 40MB+，触发 Redis 大 key 告警（一般 hash >10MB 就算偏大），且 `HSCAN` 清扫、Cluster reshard 搬一个 40MB 的 key 都很重。64 片把单分片压到 ~10MB 量级，安全。**关键**：有了 §4.4 的「单次 pipeline 取齐」，片数不再影响 RTT（永远是 1 RTT），只影响 pipeline 里的命令数（64 条 `HMGET`，仍极轻），所以放大片数几乎免费。
- **分片数跟用户数无关**——上亿用户不改变这个决策。
- 僵尸作者由 5.6 的 `HSCAN` 清理回收，不靠片数自身。

### 7.3 关注上限 1000 之后

**两个规模要分清（两个独立维度，别混）：**

- **「SCAN_LIMIT / 关注数」是「单个用户」的关注列表维度。** 用户最多关注 1000 个号（产品上限），`SCAN_LIMIT = 3000` 是「全量算」的兜底（pipeline 下扫 3000 仍 1 RTT）。关注列表由「用户缓存方案」提供，本方案只消费其取 id 接口（见 5.1）。这是**每用户、有产品上界、很小**的量。
- **`authors:lp` 的几十万 / 上千万是「全局作者」维度。** 它跨所有用户共享，保存全站作者的 `lastPostAt`，规模由作者总量决定，与单个用户关注多少无关。分片数固定 **64**（见 7.2）。

- 关注列表（来自用户缓存方案）≈ 40KB/人；`follows:read` Hash ≤ 1000 字段，一次 `HGETALL`；
- 读路径上两者交汇：把全部 ≤3000 个 followee id 作为 authorId，按 `crc32 % 64` 散到 `authors:lp` 的 64 个分片，**塞进同一个 pipeline 一次发出 = 1 RTT**（≈64 条 `HMGET`）。**瓶颈既不在段数也不在片数**——单次 pipeline + 一次内存排序，整个重算稳定在几毫秒。

## 8. 分批取 Top N（兜底）

> 当前 `SCAN_LIMIT = 3000`，§4.4 直接「一次 pipeline 取齐全部 id → 内存排序取前 N」，无需分批截断。下面的分批截断证明仅作 >SCAN_LIMIT 或内存吃紧时的兜底（理论上限的严格性保证）。

每批内部排序后只留前 N，再把各批候选合并排序取前 N —— **这在数学上是严格的，不是近似**。

> 证明：若某人排在他那一批的第 N+1 名，说明该批已有 N 个排在他前面，那么全局也至少有 N 个排在他前面，他不可能进全局前 N。所以每批只留前 N，全局前 N 一定还在候选里。

好处还有：**内存里的候选始终 ≤ N，不随关注数膨胀。**

```js
let best = []
for (let i = 0; i < ids.length; i += BATCH) {
  const rows = /* 本批算出的行 */.sort(cmp).slice(0, N)
  best = best.concat(rows).sort(cmp).slice(0, N)
}
```

`cmp` 的第三键比较 `id`，是为了让发布时间撞到同一毫秒时结果稳定，不会刷新一下顺序就变。

## 9. 边界情况清单

| 场景 | 处理 |
|---|---|
| 新关注的号 | `lastReadAt` 初始化为 `new Date(followedAt)`，否则永远显示已读 |
| 从没发过动态的号 | `lastPostAt` 为0 → 归入已读组，符合预期 |
| 作者删掉最新那条 | `$max` 只增不减，可能出现「显示未读但点进去没新内容」。低频可接受；要精确就在删除时用一次聚合重算该作者的 `max(modified_time)` |
| 关注数超 `SCAN_LIMIT`（= 3000，历史 / 水军把产品上限撑爆） | **降级但不断崖**：取最近关注的 3000 个，仍按 `lastPostAt` 倒序（用 `authors:lp` 取时间），未读一律 false。不再退化成 `followedAt` 倒序——至少保住内容时效排序。正常关注数（≤1000）走完整算法 |
| 点开瞬间作者发文（竞态） | 未读比较加 `READ_TOLERANCE`（2s）窗口吸收：点开前后 2s 内发的动态视为已读（见 3.2 / 6.2） |
| `follows:read:{uid}` 过期 / 被清（30 小时没访问） | 跟着关注列表一次回源补回 `lastReadAt`；若库里异步刷库也没落地，会短暂「全变未读」，点开一次即恢复 |
| `authors:lp` 冷字段被清理（>180 天未发） | 该号判为已读；读路径 miss 时回源 `users.lastPostAt` 补回（见 5.6） |
| redis 挂了 / 数据丢了 | 未读状态可从 `posts` 重算，`lastReadAt` 丢了最坏是「重新变未读」，不会「未读全丢且无法恢复」 |
| 普通用户和专业号混排 | 产品确认不按 `authorType` 分段，接受专业号长期占据头部（见 11.3） |

## 10. 明确不做的事

以下内容在前几轮讨论中被评估并排除，不要重新引入：

| 不做 | 原因 |
|---|---|
| 在关注表存 `hasUnread` 布尔 | 它是 (用户 × 关注对象) 维度，保持准确需要每次发布给所有粉丝写一遍，省下的只是一次内存比较 |
| 发布时给粉丝扇出写任何东西 | 百万粉的号发一条就是百万次写；本方案写侧恒为 O(1) |
| 用 ZSET 存列表 + 分数编码（未读加 1e13） | 未读是 per-user 私有的，塞进共享 score 会强迫 per-user 缓存承担全局更新频率 |
| 用 redis SET + `NOT IN` / `$nin` 反筛 | 集合一大索引就失效；本方案在内存里打标，没有反筛 |
| 分页 / 游标 | 列表长度固定，一次取全 |
| 缓存排序结果 | 见 4.5 |
| 物化未读 + 复合索引走数据库排序 | 关注上限 1000，内存排序就够了 |

## 11. 决策记录（已确认）

1. **详情缓存 = JSON String**：发布时直接 `DEL`（`user:{authorId}`），不维护单字段。理由：专业号发布频繁，反复 `HSET` 单字段不如整 key 删重建简单；「删 + 下次读回源」模型下也不存在并发覆盖问题。
2. **命名 = 「最新更新」**：实现的排序就是「最近发过动态的号排前面」，与名字一致，不再叫「最常访问」。
3. **不需要 `authorType` 分段**：专业号 vs 普通用户混排，接受专业号长期占据头部；不在 `users` 上加该字段，晚加要回填的麻烦也免了。
4. **未读判定口径 = 客户端控制**：是否标记已读完全由客户端发请求决定，服务端只负责记录 `lastReadAt`（6.2），不做「曝光即已读」之类的服务端自动判定。
5. **`lastPostAt` 兜底 = null/0 + 历史回填**：取不到（`users` 和缓存都没有）按 `null/0` 处理 → 归入已读组；旧 `users` 记录缺该字段由一次性脚本按各作者 `posts.max(modified_time)` 回填（6.4）。
6. **`follows:read:{uid}` TTL = 30 小时滑动**：比 `follows`（用户缓存方案，通常 6~12h）长，冷用户一天多后回收，回流回源补回。
7. **`authors:lp` 清理冷字段，分片数 = 64**（本轮复查修正，原 16 片/不清理）：作者量到千万级时 16 片单分片 40MB+ 触发大 key 告警 + 僵尸作者永久驻留是缓慢内存泄漏。改为 64 片（单次 pipeline 下片数不增 RTT，放大几乎免费）+ `HSCAN` 按值扫清 >180 天未发的作者，miss 回源 `users`。**前提是 §6.1 `HSET_MAX` 单调必须守住**，否则按值清扫误删活跃作者（5.5 / 5.6 / 7.2）。
8. **`SCAN_LIMIT` = 3000（原 1000）**：pipeline 下扫 3000 仍 1 RTT，故提高兜底上限；超过才降级。降级改为**不断崖**：取最近关注 3000 个、按 `lastPostAt` 倒序、未读 false（不再用 `followedAt` 倒序），保住内容时效（4.4 / 9 / 11.8）。
9. **未读比较加 `READ_TOLERANCE`（2s）窗口**（本轮新增）：吸收「点开瞬间作者发文」竞态。记录值仍取 `author.lastPostAt`（不取 `now`，避免静默丢一条）；曾考虑 `max(lastPostAt, now)` 但对竞态无效，不采用（3.2 / 6.2）。
10. **读路径网络优化：单次 pipeline 取齐**（本轮新增）：把「分 5 段、每段独立 pipeline」改成「一次 pipeline 取齐全部 ≤3000 个 id 的 lastPostAt = 1 RTT」。**不采用 Lua 全包圆**：Cluster 下多 slot `CROSSSLOT`、Lua 无 `crc32`、长脚本阻塞单线程（4.4 / 4.6）。
11. **`follows:{uid}` 不在本文范围**：关注列表的存储 / TTL / 关注取关维护由「用户缓存方案」负责，本方案只消费其取 id 接口（4.3 / 4.4 / 5.1 / 6.3）。
